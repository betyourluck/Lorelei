# Spec: 線のラベルを軽くして、ドラッグの引っかかりを消す

**ID**: 23
**Date**: 2026-10-14
**Status**: Draft（rev1。査読 3 本を反映（末尾の「査読の採否」）。P0 待ち。P0 の結果で D1〜D4 を確定させて rev2 にする）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15〜22 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 22 の後に残した候補「ドラッグ中の描き直しを軽くする」（spec 22「P2 結果」、利用者裁定で次の spec にした）。

起票前の下調べで、前提が変わった:

- spec 22 P0 の「経路の計算を止めてもフレームの間隔は 83ms、重さの大半は描き直し」は、**窓の外のノードを動かして xyflow の自動スクロールが毎フレーム走った測り**から出た数だった（failures #40）。
  ノードを窓の真ん中に置いて測り直すと、ノード 100・線 150 の図でも**経路の計算を止めればドラッグは表示の速さのまま滑らか**（フレームの間隔の 95 パーセンタイル 21.1ms）
- 引っかかるのは**経路の計算が走るフレーム**だけで（95 パーセンタイル 83〜125ms、枠のドラッグは中央値 187ms）、その中身は経路の計算（案 B の後で 1 回 14ms 前後）より、
  **経路が変わった線（1 回に 18 本前後）のラベルの描き直し**が重い。ラベルは yamada-ui の部品（ラベルの箱・矢印の種類のメニュー・削除のボタン）で、1 本 2〜2.5ms かかる
- ラベルを素の要素で描く写し（見た目だけ）にすると、95 パーセンタイルは 104ms → 21.1ms、長いフレームの中のスクリプト（言葉の定義）は 2.5 秒 → 0.08 秒になった（下調べの 2）

これを、**線のラベルを、見た目と操作を変えずに軽い部品にする**ことで直す。

変えるのはエディタの線のラベルの描き方（表示）だけ。**保存ファイル・コード生成・`read_diagram`・書き出しの出力**には何も足さない・変えない。

## 現況（2026-10-14、コードを読んで確かめた。数は下の「起票前の下調べ」）

- **線のラベル**（`features/flowchart/components/edge/editable-edge.tsx` の `EdgeContent`）: yamada-ui の `Box`（置き場所）→ `HStack` → ラベルの箱（`Box` と `span` 2 つ。押すと編集の `Input`）・
  **矢印の種類の切り替え**（`arrow-type-selector.tsx` の `ArrowTypeSelector`: `Menu` → `MenuButton`（`as={IconButton}`）と `Portal` → `MenuList` → 矢印の種類の数だけの `MenuItem`）・
  削除の `IconButton`（×）。**全部の線が、閉じているメニューごと描く**。
  rev1 で vitest（jsdom）で確かめた: 閉じた `ArrowTypeSelector` は、`role="menu"` の `MenuList` を `Portal` の先に隠して（`visibility: hidden`）描き、**矢印の種類 6 つの文字も DOM にある**。
  ただし閉じている間の項目には `role="menuitem"` が付いていない（`queryAllByRole("menuitem", { hidden: true })` も 0）。yamada-ui の `Popover` は `isLazy` を渡さない限り閉じても中身を描く（`popover-content.js` の `useLazyDisclosure`、`Menu` は `isLazy` を渡していない）。
  ブラウザで 1 本あたりどれだけ時間を食うかは確かめていない（→ P0 の 1）
- ラベルの外枠（`Box`）は `pointerEvents="all"`・`className="nodrag nopan"`・`zIndex`（枠のある図で一番上の枠の高さ + 1。`EditableEdge` の `labelZIndex`）を持つ。
  枠の面の上でボタンを押せるようにするため（failures #25）。矢印のメニューは `Portal` で文書の直下に出す（枠の中のノードに隠れない, failures #28）
- 押すと出る編集の入力欄は yamada-ui の `Input`。同時に 1 本しか編集せず、ドラッグ中の描き直しには入らない。
  編集していない間は `useEffect` でデータのラベルに合わせる（同じ ID の線を持つ別の図を開くと部品が使い回される, failures #27。`edge-content.test.tsx` のテストがある）
- `ArrowTypeSelector` を使うのは `EdgeContent` だけ（ほかは `index.ts` の再輸出と Storybook）。既存のテストは、どれもボタンを押す（クリックか Enter）か `getByRole("button")` から始まり、
  閉じたメニューの中身を見るテストは無い（`arrow-type-selector.test.tsx`・`editable-edge.test.tsx` の「矢印タイプ変更コールバック検証」は 1 回押した直後に項目を探す）
- リポジトリに自前の CSS ファイルは無い（スタイルは全部 yamada-ui の props。読む CSS は `components/providers/app-providers.tsx` の xyflow の `style.css` だけ）。
  Tauri の CSP は `style-src 'self' 'unsafe-inline'`
- `EditableEdge` は、自分の経路（`useEdgeRoute` = `useSyncExternalStore`）が変わった時と、xyflow が渡す位置が変わった時に描き直し、`EdgeContent` は memo していないので毎回描き直す。
  経路の入れ物（`EdgeRouteStore.replace`）は変わった線だけに知らせるが、経路の計算のたびに折れ線の変わる線が 18 本前後ある（下調べの 4）
- エディタ（`flow-editor.tsx`）は `useNodesState` の制御されたノードで、ノードが 1 歩動くたびに描き直し、パネル（`FlowPanel` → `PanelContent`、yamada-ui）に `nodes`・`edges` を渡すので、パネルも 1 歩ごとに描き直す。
  閉じているコード生成のダイアログ（`DownloadModal`）は毎回新しい `flowData={{ nodes, edges }}` を受けるので、`useMemo` が効かず、1 歩ごとに Mermaid のコードを生成する（1 回 0.37ms）
- ER 図の線は別の部品（`features/er-diagram/components/edge/er-editable-edge.tsx`）で、経路の計算は無い

## 起票前の下調べ（2026-10-14、ブラウザ。コミットしていない測りの口で）

測りの条件: Web 版を本番と同じ組み立て（`scripts/build-web-demo.mjs` で作業用のフォルダへ書き出し）、Browser pane を表示した状態（Chromium 152、何もしていない時のフレームの間隔 20.8ms）。
大きな図 2 つ（spec 22 の `features/flowchart/__tests__/utils/fixtures/large-*`）を取り込み、**対象のノードを窓の真ん中に置いて倍率 0.5**にし（自動スクロールを起こさない。ドラッグの前後で画面の位置が同じことを確かめた）、
合成のマウスの事件で図の座標で 10px ずつ 30 歩動かして戻した（16ms おき、spec 22 と同じ）。フレームの間隔は `requestAnimationFrame` の間隔、長いフレームはブラウザの Long Animation Frames（50ms 超）。
測りの口: 経路の計算の回ごとの時間、部品ごとの描き直しの回数、試作の切り替え（下の表の名前）。React の `Profiler` は `reactProductionProfiling` がこの静的書き出しで効かず、使えなかった。

表の列（rev1 で定義を足した。測りのスクリプトで確かめた）:

- **長いフレーム**: Long Animation Frames の記録（50ms を超えたフレーム）の数と、`duration` の計
- **スクリプト**: 長いフレームの記録の `scripts`（1 つ 5ms を超えたスクリプト）の `duration` の計。**長いフレームの中だけ**で、ドラッグ中のスクリプトの全部ではない
- **経路の計算**: 経路の計算 1 回ごとに `performance.now()` で測った時間の計。長いフレームの外の回も入る。
  なのでスクリプトより大きいことがある（`lightLabel` で 75ms 対 413ms: 経路の計算が 50ms を超えないフレームに収まり、長いフレームにならなかった）

### 下調べの限り

- `lightLabel` は見た目だけの写しで、矢印の種類のメニューを開けない。本物の実装（押した時にメニューを出す）で同じ効き目が出るかは P0 で確かめる
- `lightLabel` はインラインの `style` で描き、アイコンは lucide の SVG ではなく文字（▾・×）、色は yamada-ui の色に近い値（`#d1d5db` など）で、`:hover` は無かった（rev1 で写しの差分を読み直した）。
  外枠の `pointer-events: all`・`zIndex`・`nodrag nopan` は今と同じに持っていた。本物の形（アイコン・色・`:hover`）で同じ速さになるかも P0 で確かめる
- 合成のマウスの事件で測った（実物のマウスは事件がフレームごとにまとまる）。配布ビルド（WebView2）では測っていない
- 枠なし・取り込み直後の n57 と、枠ありの n68・F10 だけ。保存された位置と n38 は測っていない

## 言葉の定義

```text
ラベル(線)          = 線の真ん中のボタンの一式: ラベルの箱 (押すと編集) ・矢印の種類の切り替え・削除 (×)。今は EdgeContent
閉じたラベル        = 編集していない・メニューを開いていない時のラベル
引っかかり          = ドラッグ中の長いフレーム。基準は 95 パーセンタイルと、50ms を超えるフレームの数 (Long Animation Frames)
ドラッグの測り      = 下調べの条件 (本番と同じ組み立て、対象を窓の真ん中・倍率 0.5、前後で画面の位置が同じ、10px × 30 歩を往復)
長いフレームの中のスクリプト = 長いフレームの記録の scripts (1 つ 5ms 超) の duration の計。ドラッグ中のスクリプトの全部ではない (下調べの「表の列」)
24 場面             = 2 つの図 (枠あり・枠なし) × 2 つの位置 (取り込み直後・保存された位置) × 3 つのノード (n38・n57・n68) × 横と縦。spec 22 と同じ
交互の比べ          = 同じ場面を、今の main と試作で交互に測る (main → 試作 → main → 試作)。日による揺れを両方に同じにかける
```

## 決めること

### D1. ラベルをどう軽くするか

- **案 A（推奨）: 閉じたラベルを、yamada-ui の部品を使わない素の要素で描き、矢印の種類のメニューは押した時だけ出す** — ラベルの箱・矢印の切り替えのボタン・× の 3 つを素の要素にする。下調べの `lightLabel` で 95 パーセンタイル 104 → 21ms。
  - **部品の境目（rev1 で決めた）**: `EdgeContent` は今のまま `ArrowTypeSelector` を使う。`ArrowTypeSelector` が、閉じている時は素のボタンだけを描き、押す（クリック・Enter）とメニューを開いた状態で出す。
    メニューを開くのも閉じるのも `ArrowTypeSelector` の中で完結させ、`EdgeContent` は開いているかを知らない。
    `EdgeContent` が素のボタンを描いて、押した時に今の `ArrowTypeSelector` をそのまま差し込む形は採らない（今の `Menu` は閉じた状態で始まり、押した事件は素のボタンが受けたので、差し込んだだけでは開かず 2 回押すことになる。
    開いた状態で出すには `ArrowTypeSelector` 側を変えることになり、開閉の持ち主が 2 つに割れる。`arrow-type-selector.test.tsx` が本番で使わない形を見続けることにもなる）
  - **今と同じにするもの**: 見た目（色・枠・大きさ・間隔・アイコン・`:hover`）／`aria-label`（`Select arrow type`・`Delete edge`）／class（`nodrag nopan`・`arrow-type-selector-button`）／
    外枠の `pointer-events: all` と `zIndex`（枠の面の上で押せる, failures #25）／メニューを `Portal` で文書の直下に出す（枠の中のノードに隠れない, failures #28）／
    メニューの `role="menu"`・項目の `role="menuitem"`／編集していない間のラベルをデータに合わせる（failures #27）／
    振る舞い: ラベルを押すと編集・Enter で確定（IME の変換中は確定しない）・Esc で取り消し、矢印のボタンを 1 回押すか Enter でメニューが開く・項目を押すと矢印の種類が変わって閉じる・
    Esc か外を押すと閉じる・閉じた後のフォーカスは矢印のボタン、× で削除
  - **編集中の入力欄**は yamada-ui の `Input` のまま（同時に 1 本しか編集せず、ドラッグ中の描き直しに入らない）
  - **メニューの出し方（P0 で決める）**:
    - M1: yamada-ui の `Menu` を、押した時に開いた状態で出す（`defaultIsOpen` か、開閉を `ArrowTypeSelector` が持つ `isOpen`・`onClose`）。
      閉じたら `Menu` ごと外して素のボタンに戻す。1 回で開くか・素のボタンと `MenuButton` の入れ替えでフォーカスが外れないか・閉じた後にフォーカスがボタンへ戻るかを P0 で確かめる
    - M2: 同じ見た目の軽いメニューを自前で書く。`role`・矢印キーでの移り・Esc・外を押して閉じる・フォーカスの戻しを自分で持つ。
      既存のテストは role と文字と Enter で開くことしか見ないので、残りは足すテストで押さえる（P1）
  - **スタイルの書き方（rev1 で足した。推奨は S1。P0 で見た目を並べて確定）**:
    - **S1（推奨）: CSS Modules**（`features/flowchart/components/edge/` に `*.module.css`）— Next.js（14.1）の標準で依存を足さない。静的書き出し（`docs/`・`out/`）には CSS ファイルとして出て、
      Tauri の CSP（`style-src 'self'`）で読める。`:hover`・`:focus-visible` を書ける。フォーク元の改善のコミットに入れられる。リポジトリで最初の自前の CSS ファイルになる。
      vitest（jsdom）と Storybook（`@storybook/nextjs`）で読めるかは P0 で確かめる
    - S2: インラインの `style`（下調べの `lightLabel` の形）— `:hover`・`:focus-visible` を書けず、今の見た目（`_hover`）と変わる
    - S3: yamada-ui の `ui.div` など — Emotion を通るので、軽くなるかは測らないと分からない
  - 色は yamada-ui のテーマの値（`gray.300`・`blue.600`・`red.300` など）を写す。アイコンは今と同じ lucide（`ChevronDownIcon`・`XIcon`）
- 案 B: `EdgeContent` を memo する（置き場所・データ・高さが同じなら描き直さない）— 小さな直しで、95 パーセンタイル 104 → 63ms。残りで引っかかる。案 A と重ねられる。
  下調べの写しは `memo` に比べる関数を渡し、`id`・`labelX`・`labelY`・`zIndex` は値で、`data` は参照で比べた（`data` の参照が変わる描き直しでは効かない。それでも描き直しは半分になった）
- 案 C: ドラッグ中はラベルを描き直さない・隠す — 見た目が変わる（ラベルが線から離れる・消える）
- 案 D: 経路の計算で折れ線が変わる線を減らす（下調べの 4 の 18 本）— 道の選び方と離し方に手が入り、spec 17・19・21 の規則に触る。案 A の後に残る重さが見えてから

推す理由: 下調べで、引っかかりのほぼ全部がラベルの描き直しで、案 A の写しだけで消えた。見た目と操作を今と同じに保てば、使う人から見える変化は軽さだけ。
案 B は案 A の後に要るかを P0 の数で決める（`lightLabel` に `labelMemo` を重ねても、長いフレームの中のスクリプトが 75ms → 50ms になるだけで、目に見える差は無かった）。

### D2. パネルと閉じたダイアログ

- **案 A（推奨）: 今のまま（この spec では触らない）** — 下調べで、D1 の案 A の後は差が見えない（`lightLabel` 21.1ms 対 3 つ全部 21.3ms）
- 案 B: パネルに `nodes`・`edges` を渡すのをやめ、コード生成のダイアログは開いた時に今の図を読む — 1 歩ごとのパネルの描き直し（1 回 3〜9ms）と閉じたダイアログの生成が無くなる。
  フォーク元のパネルとダイアログの受け口が変わる（デスクトップの `useDesktopActions` はパネルが持つ）

### D3. 速さの基準

rev0 は「24 場面の全部で 95 パーセンタイルが 3 フレーム（62.5ms）以下」を基準にしていたが、spec 22 rev3 がブラウザの絶対の ms を基準から外した判断と食い違う（査読 2-2）。
また、何回測ってどうまとめるかが無かった（査読 3-3）。rev1 で案を分けた。P0 の後に利用者と決める。

- **案 A（推奨）: 交互の比べを主にする** — ドラッグの測りで、24 場面を今の main と案 A で交互に測る（各場面、main → 案 A → main → 案 A の 2 組。組の数は P0 で揺れを見て決める）。
  場面ごとに、2 組のフレームの間隔の 95 パーセンタイルの中央値と、長いフレームの数の和を出す。
  **合格: 24 場面の 95 パーセンタイル（場面ごとの中央値）の中央値と、長いフレームの数の 24 場面の和が、どちらも今の main より下がる**。
  62.5ms（3 フレーム）は目安として記録し、超えた場面を一覧にして利用者に見せる。枠のドラッグ（F01・F10）は記録だけ
- 案 B: rev0 の絶対の基準（24 場面の全部で 62.5ms 以下）
- spec 22 rev3 の「ブラウザの絶対の ms は日によって 2 倍近く揺れる」には、自動スクロールに汚された測りが混じっていた（failures #40）。正しい条件での揺れは分かっていないので、
  P0 で今の main の 24 場面を 2 組測って見る。揺れが小さければ案 B（か、案 A に 62.5ms を足した形）も選べる
- 速さの基準とは別に、原因の後戻りを vitest で止める: 閉じたラベルがメニューの項目を描かないこと（P1 で足すテスト）は決まった結果になるので、毎回の CI で回る

### D4. 見た目と操作を変えないことの確かめ方

- **案 A（推奨）**: Web 版の画面で、同じ図・同じ倍率で今と案 A のラベルを撮って並べる（色・大きさ・位置）。既存のテスト（`edge-content.test.tsx`・`arrow-type-selector.test.tsx`・`editable-edge.test.tsx`）は変えずに通す。
  メニューを開く（クリック・Enter）・矢印を変える・Esc と外を押して閉じる（閉じた後のフォーカス）・ラベルを編集する・消す、を画面で押して確かめる。
  枠のある図で、枠の面の上のラベルのボタンが押せることと、開いたメニューが枠の中のノードに隠れないことも押して確かめる（failures #25・#28）
- 案 B: 画素の差を比べる VRT（spec 02 の受け入れ条件 3 は未確認のまま閉じた）
