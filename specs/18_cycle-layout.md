# Spec: 取り込んだ時の段組み — 輪をほどき、どの線も下へ向く段に振る

**ID**: 18
**Date**: 2026-10-04
**Status**: **Done**（2026-10-04。rev3 → P0〜P2 着地、受け入れ条件 1〜6 通過（「P2 結果」）。P2 で見つけた枠の無い図の戻る線の件は spec 19 へ）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15〜17 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 17 P0 で見つけた（候補 ⑤）: **全部のノードに入る線がある図（閉じた輪）は、取り込むと全部が 1 段に横並びになる**。
「受付 → 審査 → 通知 → 利用者へ戻る」で「利用者」が最初のノードの図はこの形になり、AI が段の流れを書くとふつうに出てくる。
1 段に並ぶと、段を結ぶ線が全部横に走り、戻る線は図の端から端へ渡る。

起票の時にコードを読んで、根は同じ所にあると分かった: 今の段の数え方は「最初に着いた深さ」なので、**輪の無い図でも、同じ段の中を横に走る線や上へ向く線ができる**（現況）。
この spec は両方を直す: **輪をほどいてから、戻る線（D1 で決める）を除く全部の線が 1 段以上下へ向くように段を振る**。戻る線は上へ戻る（spec 17 の回り道で描く）。
Mermaid の描画（mermaid.js と merman）のどこが上・下になるかに、なるべく揃える。

変えるのは**保存した位置の無い図・ノードを並べる時**（取り込み・MCP で届いた図・枠の向きの並べ直し）だけで、保存済みの図の位置・保存・コード生成・`read_diagram` は変えない。

## 裁定（2026-10-04、利用者。P0 の後）

- **裁定 1（D1）: Mermaid と同じ** — 並べるものの順は「外とつながらない枠を定義の逆順で先に、続いてノードと外とつながる枠を出てきた順、整数に見える ID は数の順で先頭」（D1 の「並べるものの順」）。
  dagre と同じ `dfsFAS` で戻る線を選ぶ。枠のある輪では最後に定義した枠が一番上になる（人の直感とは違うが、プレビュー・書き出しと輪の切れ目が揃う）
- **裁定 2（D2）: 案 A（上からの最長路）**

## 現況（2026-10-04、コードを読んで確かめた。描画の実測は P0）

- 取り込み時の段組みは 2 か所にあり、同じ数え方をしている:
  - 枠の無い図: `features/flowchart/flow-editor.tsx:556` の `layoutNodes`（フォーク元のもの。`handleImportMermaid` の中の関数）
  - 枠のある図: `features/flowchart/utils/nested-layout.ts:50` の `levelsOf`（spec 15 で `layoutNodes` と同じ数え方として写した）。`layoutNested` が入れ物（図・枠）ごとに、
    枠をまたぐ線を `liftTo` で持ち上げてから呼ぶ。持ち上げた線の一覧（`pairs`）は元の線を**書いた順**に `Map` へ入れ、同じ 2 つを結ぶものは最初の 1 本だけ、両端が同じ（枠の中に閉じた線・自己ループ）は外す
  - spec 16 P5 の枠の向きの並べ直し（`frame-edit.ts` の `relayoutFrame`）も `layoutNested` を使う。渡すノード・線は**エディタの配列の順**。生成器もノードをこの配列の順に書き出すので、
    エディタの配列の順 = コード生成を通して Mermaid が見る順（並べ直しの時の「最初に出てきた順」はこれ）
- 数え方: **入る線の無いものを根にし、根から深さ優先で段を振る。一度訪れたものには二度と振らない**（`visited`）。根から届かないものは 0 段
  - **閉じた輪（根が無い）**: 全部 0 段 = 1 段に並ぶ（spec 17 P0 の 1 で見た）
  - **輪の外に根がある図**（開始 → 利用者 → 受付 → … → 利用者）: 段に分かれ、戻る線は上へ戻る（spec 17 P0 の格子はこの形にして測った）
  - **根から届かない輪が別にある図**: その輪は全部 0 段で、根と同じ段に並ぶ
  - **輪が無くても、段は「最初に着いた深さ」**: `A → B`・`A → C`・`C → B` で `A → B` が先に書いてあると、B と C が同じ 1 段になり、`C → B` が横に走る。`Math.max(…)` は訪れた時に 1 回しか呼ばれないので効いていない
  - フォーク元の `layoutNodes` は自己ループ（`A → A`）を外さないが、`visited` があるので止まる
- 同じ段の中の並びは、深さ優先で訪れた順（段の `Map` に入った順）。線の交差を減らす並べ替えは無い
- `itemsOf`（`layoutNested` が入れ物の中に並べるもの）は**ノードを先に、枠を後に**並べる（`data.nodes` の順、続いて `data.subgraphs` の順）。Mermaid のソースの中での枠とノードの前後は持っていない
- デスクトップで MCP の `open_in_editor` / `update_diagram` から届いた図も、同じ `handleImportMermaid` を通る（`lib/desktop/use-desktop-open.ts` の `onImport`）。Rust の側に配置は無い
- Mermaid の描画（mermaid.js 11.17.2 の `dagre-d3-es` 7.0.14、`src/dagre/acyclic.js` と `rank/index.js` を読んだ）:
  - **輪のほどき方（`dfsFAS`）**: ノードを**グラフに入った順**（`g.nodes()`）に深さ優先でたどり、たどっている途中の祖先へ戻る線を逆向きにする（描く時に戻す）。
    設定 `acyclicer: "greedy"` の時だけ別の方法（`greedyFAS`）。自己ループは dagre が輪のほどきの前に外す見込み（P0 の 1 で確かめる）
  - **段の振り方**: 既定は network simplex（線の長さの合計を最小にする。全部の線は 1 段以上下へ）。ほかに `longest-path`（**下から**: 出る線の無いものを揃え、`rank(v) = min(rank(w) − 1)`）・`tight-tree`
  - mermaid の flowchart が渡す `acyclicer`・`ranker`、**ノードと枠をグラフに入れる順**（flowDb の頂点の順か、並べ替えるか、枠を先に入れるか）は確かめていない（P0 の 1）。merman も同じ（`dugong` などの写しの見込み）

## 言葉の定義（D1〜D3 で同じ意味に使う）

```text
並べるもの      = 入れ物（図・枠）の中に直接並ぶノードと枠（itemsOf）。並べるものの順は D1 で決める
線              = 入れ物の中の線（枠をまたぐ線は liftTo で持ち上げた後。両端が同じものは外す = 自己ループと、枠の中に閉じた線）。線の順は元の線を書いた順
戻る線          = D1 で選ぶ線。段を数える時だけ逆向きにする（線の向き・保存・描画は変えない）
段の条件        = 戻る線を除く全部の線 (u, v) で 段(u) < 段(v)、戻る線 (u, v) で 段(u) > 段(v)。どの線も同じ段の中を横に走らない
```

## 決めること

### D1. 輪のほどき方（**裁定 1**）

**P0 の後の推奨: 案 A を、P0 で分かった Mermaid の入れ方そのままに写す（下の「並べるものの順」）**。この規則の下書きは P0 の格子 20 通り・69 本の線の上下が Mermaid と全部一致した（今の数え方は 22 本、案 B は 55 本）

並べるものの順（P0 の 1・2 で確かめた mermaid.js の flowDb `getData` と graphlib の `g.nodes()` の順を、入れ物ごとに写す）:

```text
1. 外とつながらない枠（spec 16 の external(F) が偽）を、枠の一覧（getSubGraphs の順）の**逆順**で先に
2. 続いて、ノード（最初に出てきた順）と、外とつながる枠を、出てきた順に混ぜて並べる。外とつながる枠の位置は、その子孫のノードで最初に出てきたものの位置
   （Mermaid は外とつながる枠への線を中のノードへ付け替えるので、輪をたどり始める所はそのノードになる。P0 の c18）
3. 最後に、整数に見える ID（0 から 2^32−2 の十進表記）を全部、数の順に先頭へ出す（graphlib はノードをオブジェクトのキーで持つので、JS のキーの順になる。P0 の c17）
線の順 = 書いた順（持ち上げた後）。自己ループと両端が同じ線は外す
```


- **案 A（推奨。P0 の 1 で、mermaid.js が並べるものを入れる順を写せると分かった場合）: dagre と同じ `dfsFAS`** — 並べるものを順にたどり始め（まだ訪れていなければ）、
  線を書いた順に深さ優先でたどる。たどっている途中の祖先へ戻る線を戻る線にする
  - 閉じた輪では、**順が最初のものが一番上**になる（`利用者 → 受付 → 審査 → 通知 → 利用者` で利用者が最初なら、利用者が上、通知 → 利用者が戻る線）
  - **並べるものの順**は、P0 の 1 で確かめた mermaid.js の入れ方に合わせる（ノードと枠の前後を含む。査読 2-4）。合わせられない時（入れ方がソースの順から決まらない等）は案 B
  - 並べ直し（`relayoutFrame`）では、エディタの配列の順を使う（現況: 生成器が書き出す順と同じ。査読 2-5）。配列の順は、ノードを足す・付け替える（`sortParentsFirst`）時だけ変わる
- 案 B: 今の「根からの深さ優先」は残し、根から届かないものがあれば、その中で順が最初のものを根に足して続ける（輪の無い図・根から届く輪は今と同じ戻る線になる）
- 案 C: 線の重みで戻る線を選ぶ（`greedyFAS`）。戻る線の本数は少なくなりやすいが、どれが戻る線になるかを人が読みにくい

### D2. 段の振り方（**裁定 2**。P0 の 2 で決める）

戻る線を逆向きにした（輪の無い）グラフで、段の条件を満たすように振る。どの案でも段の条件は満たす。違いは「線が長くなる所をどこに作るか」。

- **案 A（推奨。P0 の後も変えない）: 上からの最長路** — `段(v) = 0`（入る線が無い）、`max(段(u) + 1)`（入る線の元 u）。入る線の無いもの（根）は全部 0 段なので、
  深い所へ 1 本だけ入る根は、その相手から遠い上の段に置かれる。**現況の段が段の条件を満たしている図では、段は今と同じになる**（証明: 今の段は根からの道の長さなので最長路以下、段の条件があれば帰納的に最長路以上）
- 案 B: dagre の段の振り方を使う（network simplex。`@dagrejs/dagre` を依存に足して段だけ取るか、`dagre-d3-es` の段の部分を写す） — Mermaid と同じ段になる見込みだが、依存かコードが大きい。
  輪の無い図でも、段の条件を満たしている今の配置が変わりうる
- 案 C: 下からの最長路（dagre の `longest-path`） — 出る線の無いもの（葉）が全部いちばん下の段に揃うので、早い段から出て終わる線が長くなる
- 案 0: 今の数え方を残し、D1 の輪のほどき方だけ足す — 輪の無い図は一字一句変わらないが、現況の「横に走る線」は残る（Goal の後半を外す。題も変える）

（rev0 の案 B「根を下へ寄せる」は、対象と繰り返しの定義が無く（査読 1-3）、鎖になった根の側に効かない（査読 2-2）ので外した）

P0 の後の推奨の理由: 線ごとの上下は D1 だけで決まり（段の条件を満たせば、戻る線は上・ほかは下）、P0 の格子で Mermaid と全部一致した。段の数が Mermaid と違うのは「深い所へ 1 本だけ入る根」（c15: Mermaid は X を 2 段目、案 A は 0 段目）だけ。
fixture 30 通りで段が変わるのは閉じた輪の 1 通りだけ、テストの期待は 1 つも変わらない（P0 の 3）。案 B（dagre を依存に足す）の得は根の段だけで、依存かコードの重さに見合わない。
仮の推奨の理由（rev1）: 段の条件を満たし、今の配置で段の条件を満たしている図は変えない（受け入れ条件 3 を「変わらない」と書ける）。
Mermaid との違いは「根・葉の段」に出る見込みなので、P0 の 2 で **線ごとの上下（戻る線か・下へ向くか）** が Mermaid と揃うかを数え、揃わないものが多ければ案 B にする

### D3. 計算の形と置き場所

- 1 つの純粋な関数にする（`nested-layout.ts`。`levelsOf` を作り直す。名前は変えるかもしれない）: 入力は並べるもの（順つき）と線（順つき）、出力は段と、同じ段の中の並び
  - **自己ループと両端が同じ線は、輪のほどきにも段の数えにも入れない**（入れると最長路が `段(A) = 段(A) + 1` になる。査読 1・2-1。`layoutNested` は今も外している。`layoutNodes` の分は新しく外す）
  - **`visited` で振り直しを止める形はやめる**: 戻る線を逆向きにした後、トポロジカル順に最長路を数える（査読 1。`Math.max` が効かない今の不具合を繰り返さない）
  - **同じ段の中の並び**: 今と同じ「深さ優先で訪れた順」（並べるものの順にたどり始め、線を書いた順）。D1 の案 A のたどり方と同じ順になる。
    段が変わったものは並ぶ段が変わるので、その段の並びも変わる（避けられない。D2 の案 A なら、段が変わらない図は並びも変わらない）
- `flow-editor.tsx` の `layoutNodes` の段の数え方を、その関数を呼ぶ形にする（フォーク元の重複を 1 つにする）。位置の計算（`placeByDirection`）は変えない
- `layoutNested` は今のまま入れ物ごとに呼ぶ（枠をまたぐ線は `liftTo` で持ち上げた後）。`relayoutFrame` も同じ関数を通る
- 並べるものの順（D1）は、`itemsOf` の「ノードが先・枠が後」を P0 の 1 の結果に合わせて変えるかを決める

### D4. 変わるもの・変えないもの

- 変わる: **保存した位置の無い図・ノードを並べる時**の配置 = Web 版のインポート、デスクトップのツールバーのインポート、MCP の `open_in_editor` の新しい図・`update_diagram` で増えたノード（spec 15 D4）、
  新規作成の初期図（`initialFlowNodes`。位置の無い図を並べる経路を通るなら）、枠の向きを見出しで変えた時の並べ直し（spec 16 P5）
- 変えない: 保存済みの図を開いた時の位置（`Document.layout` を当てる）・生成器・保存・`read_diagram`・Rust
- D2 が案 A なら、輪の無い図は「今の段が段の条件を満たしていない図」だけが変わる。案 B・C なら、それ以外も変わりうる（P0 の 3 で数える）

## 受け入れ条件

1. 閉じた輪の図（枠あり・なし、`TD`・`LR`）を取り込むと、段に分かれて並ぶ（1 段に並ばない）。どれが上になるかは D1 の規則どおり
2. 取り込んだ図は段の条件を満たす（戻る線を除く全部の線が下へ向き、戻る線は上へ戻り、同じ段の中を横に走る線が無い）
3. P0 の 2 の格子で、**線ごとの上下（下へ向くか・上へ戻るか）**が mermaid.js と揃う。段の数（何段目か）の違いは許す。揃わない線は spec に理由を書いて残す（査読 1-4 の 5）
4. 輪の無い図で、今の配置が段の条件を満たしている図は、配置が一字一句変わらない（D2 が案 A の場合。案 B・C なら P0 の 3 で数えた図の一覧を spec に書き、P1 でその一覧と一致する）
5. 保存済みの図を開き直した位置は変わらない。保存・コード生成・`read_diagram` の出力は変わらない
6. Web 版（GitHub Pages）のフローチャートのエディタで 1〜3 ができる（デスクトップ専用の変更を含まない）

## スコープ外

- 同じ段の中の並べ替え（線の交差を減らす。Mermaid の `order`）
- 段の中の位置の詰め方（Mermaid の `position`。今の中央揃えのまま）
- 保存済みの図を並べ直す操作（図全体の「並べ直し」ボタンなど）
- 戻る線の描き方（spec 17 の回り道のまま）
- ER 図の配置

  曲線の中点（x ≈ 1118）が 実行 → 評価 の線の中点とほぼ同じ所で、2 つのボタンが重なって 1 つしか見えない。枠の無い閉じた輪の「完了」も、中点が発送と取り寄せの隙間（16px）に当たり、ボタンがノードの後ろに隠れた
- 原因は spec 17 の裁定 1（両端とも図の直下の線は、同じ高さのノードの後ろに隠れるだけなので回さない）。spec 18 で閉じた輪が段に分かれ、枠の無い図にも戻る線がふつうに出るようになったので、隠れた線とボタンが目立つようになった。
  「枠の無い図でも、曲線かボタンがノードに重なる線は回す」として spec 19 で見直す（利用者裁定 2026-10-04）
