# Spec: 枠の無い図でも、ノードを貫く線を外へ回す

**ID**: 19
**Date**: 2026-10-04
**Status**: **Done**（rev3。P0〜P2 着地、受け入れ条件 1〜6 通過（4 は際）。裁定 1・2 と D3・D4 は rev2 で確定）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15〜18 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 18 P2 で見つけた（候補 ⑧）: **枠の無い図の戻る線が見えず、ラベルのボタンが押せない**。

- LR の閉じた輪 `計画 → 実行 → 評価 → 改善 → 計画` の 改善 → 計画 は、曲線が y 一定の直線になって 4 つのノードを真横に貫き、ノードの後ろに隠れる。
  曲線の中点が 実行 → 評価 の線の中点とほぼ同じ所で、2 つのボタンが重なって 1 つしか見えない（利用者の言「改善から計画に戻るときに回り込みは発生していない」）
- 枠の無い閉じた輪の「完了」（入金確認 → 注文受付）は、曲線の中点が発送と取り寄せの隙間に当たり、ボタンがノードの後ろに隠れた
  （P0 の 1: 曲線そのものが在庫確認・請求を貫き、ボタンは発送と取り寄せにかかっていた）

spec 17 の裁定 1 で、両端とも図の直下の線は「同じ高さのノードの後ろに隠れるだけ」なので回さないと決めた。spec 18 で閉じた輪が段に分かれ、枠の無い図にも戻る線がふつうに出るようになり、
隠れた線と押せないボタンが目立つようになった。これを、**枠の無い図でも、ノードを貫く線は spec 17 の回り道で外へ回し、ノードの後ろに隠れたボタンは見える所へ出す**ようにする。

**この spec は spec 17 の裁定 1 を改める**（spec 17 で採らなかった案 B を、条件を足して採り直す）。spec 17 の裁定 1 の節と data_contract の `editor_frame` の説明は、P1 の台帳のコミットで改める（改めた旨と、この spec への参照を書く）。

変えるのはエディタの線の描き方（表示）だけ。**保存ファイル・コード生成・`read_diagram`・書き出しの出力**には何も足さない・変えない（spec 17 と同じ）。台帳の説明は上のとおり改める。

## 裁定（2026-10-04、利用者。P0 の後）

- **裁定 1（D1）: 案 A** — 枠と全部のノード（高さを問わない）を回す対象にする。段を飛ばす線が線ごと・ボタンごと隠れるのを防ぎ、Goal を満たすため（P0 の 4）
- **裁定 2（D2）: 案 C** — ノードとの交わりでは、曲線がノードを貫く時か、ボタンが縦横とも 12px（`ROUTE.MARGIN`）以上ノードにかかる時に回す。
  かすりでの回り道を防ぎ、隙間を通る線のボタンが丸ごと隠れる形（P0 の 2 の反例）は拾う。案 D（ボタンだけずらす）の新しい仕組みは入れない
- **D3: 案 A'** — 回した線のボタンは、回さない線のボタンも避ける。回さない線のボタンは動かさない
- **D4: 基準を中央値にする** — ノード 110・線 150 の図で、ドラッグ中の 1 回の**中央値** 33ms 以下、全部の計算 1 回 100ms 以下

## 現況（2026-10-04、コードを読んで確かめた。画面の測りは P0）

- 回すかの判定は `features/flowchart/utils/edge-route.ts` の `needsRoute`（spec 17 裁定 1 = 案 A）: 今の曲線、または曲線の中点のボタンが、
  **どちらの端も中にいない枠**・**線の高さより低いノード**・**端である枠の内側**のどれかと交わる線だけを回す（`pathHits(curve, r) || rectsOverlap(button, r)`）。
  線の高さ = 端のうち親を持つものの高さの大きい方（xyflow の `getElevatedEdgeZIndex`）なので、**両端とも図の直下の線（高さ 0）は、ノード（高さ 0）と交わっても回さない**。
  同じ枠の中の 2 つのノードを結ぶ線も、同じ枠の中のほかのノード（同じ高さ）とは交わっても回さない
- **端そのものと端の祖先の枠は、はじめから判定の外**（`viewOf` の `obstacles` は端 2 つと端の祖先の枠を除いたもの。判定に入る端は「端である枠の内側」だけ）。
  曲線の始まりと終わりはノードの縁なので、端を外さないと全部の線が当たる — 今の形はそれを外している
- **回すと決めた線の道筋は、高さを問わず障害物の全部（端でも端の祖先でもない枠とノード）を避ける**（`routeOne` の `avoid`。spec 17「言葉の定義」の「回すか」と「避けるもの」は別の集まり）。
  通れる枠（端の祖先）は本体を避けず見出しの帯だけを避ける。この spec は「回すか」だけを変え、「避けるもの」は変えない
- spec 17 P0 の 4: 線の高さ = ノードの高さの時は、ノードが線の上に描かれて線を隠す。ボタン（`EdgeLabelRenderer`）もノードより下の層に描かれる（failures #25。枠のある図では spec 17 で線のラベルを枠より上に上げたが、ノードより下のまま）
- ボタンは 101×28（ラベルが空）〜 1 行のまま伸びる（長いラベルで 330×28）（spec 17 P0）。曲線は細いが、ボタンは広い
- 回した線のボタンは `placeButton` が置く（spec 17 D3）: 避けるもの（障害物・端・通れる枠の見出し）と、**先に置いた回した線のボタン**と重ならない所。
  **回さない線のボタンは避けない**（`taken` に入るのは回した線のボタンだけ）。回さない線のボタンは線の部品が曲線の中点に置き、互いに逆向きの組だけ `adjustEdgeLabelPosition`（`features/flowchart/hooks/edge-layout.ts`）でずらす
- **エディタは段を持たない**: 段（spec 18）は取り込み・並べ直しの時に位置を決めるのに使うだけで、`routeEdges` に渡るのはノード・枠の矩形と線の接続点だけ。
  人がノードを動かした後は段と位置が食い違う。回すかの判定に「戻る線か」を使うなら、位置から決める必要がある
- spec 17 の裁定 1 の案 B（枠とノードの両方を回す対象にする）は「Web 版の枠の無い図の見た目が変わる。ノードの後ろに隠れているだけの線まで回す」として採らなかった。
  その時は、枠の無い図の戻る線は「輪の外に根がある図」でしか段に分かれず（閉じた輪は 1 段に並んでいた）、目立たなかった。
  spec 17 P0 の下書き（node）では、案 B で回す線は 8 本 → 15 本、判定と探索は中央値 7.5〜8.7ms → 13.3ms だった
- 速さ（spec 17 P1、ブラウザ）: ノード 110・線 150 の図で、回す線 58 本、全部の計算 36ms、ドラッグ中の 1 回 22ms（関わる 13 本だけ探し直す）。
  ドラッグ中に 1 回が 8ms を超えた時だけ、次の計算をその時間の 2 倍遅らせる（`hooks/use-edge-routes.ts`）。ドラッグを終えた時は必ず全部を計算し直す

## 言葉の定義（D1〜D4 で同じ意味に使う）

```text
端(線)            = 線の出口と入口のノード・枠
通れる枠(線)      = 端の祖先の枠
判定の対象(線)    = 端でも通れる枠でもない枠とノード（＝ spec 17 の 障害物(線)）＋ 端である枠の内側
ボタン(線)        = 今の曲線の中点に置いた、線のラベルのボタンの矩形（estimateButtonSize の大きさ）
かかる深さ(b, r)  = ボタン b と矩形 r の重なりの、横の幅と縦の幅の小さい方（重ならなければ 0）
回すか(線)        = 次のどれかに当たる（裁定 1 の案 A・裁定 2 の案 C）
                    ・今の曲線かボタンが、判定の対象の枠（端である枠の内側を含む）と交わる（spec 17 のまま）
                    ・今の曲線が、判定の対象のノード（高さを問わない）を貫く
                    ・ボタンが、判定の対象のノードに、かかる深さ 12px（ROUTE.MARGIN）以上でかかる
避けるもの(線)    = 判定の対象の全部（高さを問わない）＋ 通れる枠の見出しの帯。回すと決めた線の道筋はこれを避ける（spec 17 のまま、この spec では変えない）
戻る線(線)        = 入口の接続点が、出口の接続点の向きの後ろにある線（出口が下の辺なら 入口の y < 出口の y、上の辺なら逆、右の辺なら 入口の x < 出口の x、左の辺なら逆）。
                    今の位置で決める。取り込んだ直後の図では spec 18 の「戻る線」（dfsFAS が逆向きに数えた線）と一致する。
                    裁定 1 で案 B を採らなかったので、判定には使わない（P0 で案 B を数えた時の定義）
```

## 決めること

### D1. 回す対象（**裁定 1 = 案 A**。spec 17 の裁定 1 を改める）

どの案も、端そのものと通れる枠は判定に入らない（現況のとおり）。避けるものは変えない。

- **案 A（採用）: 枠と、全部のノード** — 判定の対象のうち、枠（端である枠の内側を含む）と、**高さを問わない全部のノード**を回す対象にする（spec 17 の案 B）。
  枠の無い図の戻る線・段を飛ばす線（`A → B → C` と `A → C`）も、同じ枠の中のノードを貫く線も回る。回さない線の形は今のまま。
  **枠のある図も変わる**: 両端とも図の直下の線と、同じ枠の中のノードどうしの線が、同じ高さのノードを貫く時に回るようになる
- 案 B: 枠と、戻る線が貫くノード — 案 A の対象のうち、ノードとの交わりで回すのは**戻る線**（言葉の定義。今の位置で決める）だけ。
  段を飛ばす順向きの線（`A → C`）はノードの後ろに隠れたままなので、**Goal の「ノードを貫く線は外へ回す」は戻る線の分しか満たさない**
- 案 C: ボタンだけ — 中点のボタンがノード・ほかの線のボタンと重なる線だけを足す。**Goal の 1 つ目（LR の閉じた輪で線そのものがノードの後ろに隠れる）を満たさない**。比べるための案

採った理由: 隠れる線は戻る線だけでなく、段を飛ばす線も同じ（ノードの後ろを通るので、どこへつながっているか読めない）。spec 17 の回り道は図全体で 1 回に計算し、回した線どうしの重なりとボタンも離すので、対象を広げても形は崩れない。

**代わりに見た目が変わる**: 回した線は縦と横の線分（角の丸め 8px）なので、`A → B`・`B → C` が滑らかな曲線のまま、`A → C` だけ角張った回り道になる。
分岐と合流のバイパス線は、曲線のままでも（ノードをかすめるだけなら）読めることがある。Web 版の枠の無い図の見た目は「ノードを貫く線がある図」だけ変わる。
P0 の 2 で変わる図と線を数え、P0 の 4 で案 A と案 B の違いを撮って、**利用者が画面を見てから裁定する**。

→ P0: 案 B は段を飛ばす線を線ごと・ボタンごと隠したまま残した（P0 の 4）。案 A で、枠の無い大きな図は 150 本中 54 本が回り、ドラッグ中の中央値が 1ms → 11〜33ms（P0 の 3）。利用者が案 A に裁定した

### D2. ボタンだけがノードにかかる線（**裁定 2 = 案 C**）

spec 17 の判定は「曲線、**またはボタン**が対象と交わる」で、ボタンだけが枠にかかる線も回す（spec 17 P1 の画面の LR の e）。
対象を全部のノードに広げると、曲線はノードの間を普通に結ぶのに、幅 101〜330px のボタンの端がとなりのノードの角に 1px かかっただけで、線全体が回り道になる。

- 案 A: 曲線だけ — ノードとの交わりは曲線だけで見る（枠は今のまま、ボタンも見る）。ボタンだけがノードにかかる線は、線もボタンも今のまま（隠れたまま）
- 案 B: 曲線かボタン（rev0 の形、spec 17 の枠と同じ）— かすっただけで回る
- **案 C（採用）: 曲線か、深くかかったボタン** — ボタンとノードの重なりが縦横とも `ROUTE.MARGIN`（12px）以上の時だけ回す。かすりは回さない
- 案 D（rev1 の仮の推奨）: 曲線だけ回し、ボタンはずらす — ノードとの交わりは曲線だけで回すか決める（案 A と同じ）。ボタンだけがノードにかかる回さない線は、
  曲線のまま、ボタンを**曲線の上で中点に近い順に**ノードと重ならない所へずらす（`placeButton` の考え方を曲線を刻んだ点の上で使う）。置けなければ今の中点

rev1 で仮に推した理由: 線の形を変えずにボタンだけを見える所へ出せる（査読 2 の 1 の提案）。ただし、回さない線のボタンの位置を `routeEdges` が返すことになり、返す形（`EdgeRoute` は折れ線を持つ）と線の部品の受け方が増える。
**「完了」の件がボタンだけの場合（P0 の 1）に案 A は Goal を満たさない**。P0 の 1 で「完了」の曲線がノードを貫くか、P0 の 2 で「ボタンだけがノードにかかる線」の本数とかかる深さを数え、
数が少なく浅いなら案 C、Goal に要るなら案 D、と P0 の後に決める。

→ P0: 「完了」は曲線そのものがノードを貫く線で、ボタンだけがかかる線は手元の図に 0 本だった。ただし、横に 10px の隙間で並ぶ 2 つのノードの間をまっすぐ通る線は、
ボタンが縦に 28px 丸ごとかかる（P0 の 2 の反例。案 A では隠れたまま）。利用者が案 C に裁定した（案 D の新しい仕組みは要らない）。
枠との交わりは今のまま（曲線か、かかる深さを問わないボタン。spec 17 P1 の LR の e）

### D3. ボタンどうしの重なり（**案 A'** に決定）

- 案 A: 回さない線のボタンどうしの重なりは扱わない（スコープ外、候補 ⑦）。回した線のボタンは今のまま、避けるものと回した線のボタンだけを避ける
- **案 A'（採用）**: 案 A に加えて、**回した線のボタンは、回さない線のボタン（今の位置）も避ける**。回さない線のボタンは動かさない。
  回さない線のボタンの位置は、線の部品と同じ計算（曲線の中点と `adjustEdgeLabelPosition`）で求めて `placeButton` の `taken` に先に入れる
- 案 B: 回さない線のボタンも、spec 17 D3 のボタンの置き方（重ならない所へずらす）に入れる

理由: LR の閉じた輪では、改善 → 計画（回す）と 実行 → 評価（回さない）のボタンが今は同じ所にある。回した線の道筋は輪の外を通るので、
回した線の一番長い線分の中点は 実行 → 評価 のボタンから離れる見込みだが、`placeButton` は回さない線のボタンを見ないので、重ならないことは保証されない。
案 A' なら受け入れ条件 2 の「ほかのボタンと重ならない」を、回した線について保証できる。回さない線どうしは動かさないので、見た目の変化は回した線のボタンだけに留まる。
P0 で、段を飛ばす線の TD・RL・格子の c14・反例の 3 つ並ぶ図で、回した線のボタンが回さない線のボタンに重なった（P0 の 2・4）。

P1 で決めること: `adjustEdgeLabelPosition`（`hooks/edge-layout.ts`）は線の部品の側にあるので、`routeEdges` が回さない線のボタンの位置を求める時に同じ式を通す形
（関数を `utils/` へ移して両方から使う、など）。ずらした結果が部品の描く位置と食い違えば、案 A' の保証が崩れる

**直らないもの**（案 A・A' とも）: 回さない線どうしのボタンの重なり（順向きの線どうし、など）はそのまま残る。LR の閉じた輪の重なりが消えるのは、片方が回されてボタンが退くから。
ボタンの重なり全般が直るのではない（候補 ⑦ のまま）。P0 の画面では、回すと隠れていた線が外へ出るので、回さない線どうしの重なりも減った（枠の無い大きな図で 53 組 → 11 組）

### D4. 速さ（**基準を中央値に**改める）

- 回す線が増える（枠の無い図の戻る線・飛ばす線）。spec 17 P1 の測りに足して、回す線が何本・何 ms 増えるかを P0 の 3 で測る
- **基準**: ノード 110・線 150 の図（枠のある図と、枠を外した図の両方）で
  - **ドラッグ中の 1 回の中央値: 33ms 以下**（30fps。重い時は spec 17 の間引きで付いてくる — その形を保てる上限）。
    rev1 は「1 回」（最大）にしていたが、P0 で今のコード（spec 17）でも最大は 35〜45ms と超え、最大は 1 回だけの跳ね（ごみ集め・描き直し）で揺れたので中央値にした。
    測る時は、窓が隠れた環境では今のコードの値も同じ環境で測って並べる（P0 の 3）
  - **全部の計算 1 回: 100ms 以下**（取り込み・ドラッグを終えた時。人が待たされたと感じない上限）
- P0 の 3 の値（案 A）: 全部の計算は枠あり 60ms・枠なし 44ms、ドラッグ中の中央値は枠あり 16〜26ms・枠なし 11〜33ms。基準の内側だが、枠の無い図の 33ms は際
- 基準を超えたら、P1 で先に絞る（判定を外接矩形で絞る・ドラッグ中に探し直す線を、動いたものの外接矩形と交わる線だけにする, spec 17 D4 の案 iii の延長）。絞っても超えるなら裁定 1 を案 B に戻すかを利用者に諮る
