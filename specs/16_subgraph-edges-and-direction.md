# Spec: サブグラフを指す線と、サブグラフの中の向きをエディタで扱う

**ID**: 16
**Date**: 2026-10-01
**Status**: **Draft rev2**（rev0 起票 → 査読 2 本を rev1 に反映 → P0 の結果で rev2。裁定 1〜3 を待つ。spec 15 P5 の持ち越し）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15 と同じく、**フォーク元の改善とデスクトップ・Rust・台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 15 で枠（サブグラフ）はエディタに載ったが、落とし続けているものが 2 つある（spec 15 D6）:

1. **サブグラフを指す線**（`A --> 審査`・`審査 --> 通知`・`受付 --> 審査`）— 取り込みで落とし `edge_to_subgraph` として数える
2. **サブグラフの中の `direction`**（`subgraph 審査` の中の `direction LR`）— 取り込みで落とし `subgraph_direction` として数える

AI は段の流れを「枠から枠へ」の線で書き、枠の中を横に並べるために `direction` を書く。どちらもデスクトップで開くと最初の自動保存で消え、
`read_diagram` で読み戻しても戻らない。これを**取り込み・表示・保存・`read_diagram`・コード生成で落とさず、GUI で作れる・変えられる**ようにする。

あわせて、**エディタの枠の中の並びと接続点を、Mermaid の描画で効く向きに合わせるか**を決める（D4、裁定 1）。下の「現況」のとおり、
Mermaid の描画では枠の中の `direction` は**いつも効くわけではなく**、向きの無い枠が図と逆向きに並ぶこともある。

## 裁定（未。利用者が決める）

- **裁定 1（D4）**: エディタの枠の中の並びと接続点を、描画で効く向きに合わせるか — 推奨は**案 B**（rev0 の案 A から rev1 で変えた。査読 2-5）。
  P0 で効く向きの規則は 520 点で描画と一致したので、案 A も正確に作れる。違いは線の操作で接続点が跳ねるかどうかだけ
- **裁定 2（D2）**: 枠と自分の中（子孫）を結ぶ線の扱い — P0 の 1 の結果から推奨は**案 B**（落として数え、GUI でも作らせない。枠の自己ループは写す）
- **裁定 3（D1）**: 枠の中の `direction TD` を `TB` にそろえるか — P0 の 3・4 の結果から推奨は**案 A**（そろえる。mermaid.js と merman の食い違いもそろえると消える）

## 現況（2026-10-01、コードを読んで確かめた。描画の実測は P0）

### 取り込み（TS・Rust）

- TS: `features/flowchart/utils/from-mermaid.ts:100〜104` で、線の両端のどちらかがノードの ID に無い（= 枠の ID）時、`edge_to_subgraph` として落とす。
  `:120` で `dir` を持つ枠の数を `subgraph_direction` として数える。材料の `snapshot.subgraphs[].dir`（`components/ui/mermaid-snapshot.ts:37`）は**手元にある**
- Rust: `crates/lorelei_core/src/editor.rs:309〜312` で同じく落とし、`:223〜229` で `dir` が null でない枠を数える。`FlowSubgraph` に向きの欄は無い
- 枠と同じ ID のノードは作らない（spec 15 D1。mermaid.js も merman も、線が枠を指すとその ID のノードも作るため）。この規則はそのまま使える — 線の行き先を枠にすればよい
- インポートのダイアログの黄色の印（`features/flowchart/utils/drop-warnings.ts:78・84`）は、枠の中の `direction` の行と、枠の ID を端に持つ線の行に付く

### エディタ・生成器・配置

- 枠は `subgraphNode`（`components/node/subgraph-node.tsx`）。**接続点（`Handle`）を持たない**。本体は `pointer-events: none`（`FRAME_NODE_STYLE`、failures #25）で、
  見出し（上の辺の 28px、`pointer-events: all`）・× ・選んだ時の右と下の辺のつまみ（`ResizeControlVariant.Line`）だけが押す操作を受ける
- xyflow の接続点の CSS は `.react-flow__handle { pointer-events: none }` で、繋げる状態の時だけ接続点自身に `pointer-events: all` が付く（`@xyflow/react/dist/style.css`）。
  子が自分で `all` を持てば親の `none` に関わらず届く（spec 15 の見出しがこの形で動いている）。ただし見出し・つまみとの重なりは測っていない（P0 の 5）
- ノードの接続点は図全体の向きで決まる（`editable-node.tsx:31〜34` の `useDirection()` → `handlePositions`。`DirectionContext` は図に 1 つ）。枠の中かどうかは見ない
- **線を引いて空いた所へ落とした時の解析が、`-` を含む ID で壊れる**（`hooks/flow-helpers.ts:83〜89` の `parseConnectingNodeId` が `split("-")` の最初の 2 つを取る。
  `onConnectStart` は `${nodeId}-${handleType}` を作る）。取り込んだ `a-b` のようなノードで**今も**壊れている（元のノードが見つからず何も起きない）。GUI の枠の ID は `frame-group1-<時刻>` なので必ず壊れる
- 生成器（`hooks/mermaid.ts:342〜360`）は線を全部最後に外へ書き、**両端のどちらかが枠の線は書かない**（「枠を指す線はエディタでは作れない」）。枠の中に `direction` の行は書かない
- 取り込み時の配置（`utils/nested-layout.ts` の `layoutNested`）は、図全体の向き 1 つで全部の枠の中を並べる。枠をまたぐ線は「同じ枠の中に並ぶ祖先」へ持ち上げる（`liftTo`）。
  `parentOf` に枠も入っているので、端が枠そのものの線も持ち上がる: その枠の外では枠として数え、その枠の中では無視する。
  **枠と自分の子孫を結ぶ線（`審査 --> C`、`C` は `審査` の中）はどの段組みにも効かない**（外では両端が `審査` に持ち上がって同じ点、中では `審査` が外にいる）。`C` は入る線の無いものとして並ぶ（査読 2-7）
- 図の向きを変えても位置は並べ直さず、接続点だけが動く（spec 07。`flow-editor.tsx:655` の `onDirectionChange={setDirection}`）
- 向きのメニュー `DirectionMenu`（`components/direction-menu.tsx`）は `GraphType`（`TD`・`LR`・`RL`・`BT`）だけで「指定なし」を持たず、`size="sm"`（見出しの 28px より高い）

### Mermaid の描画での枠の向き（ソースを読んだ。**P0 で描画を測って確かめた** — 1・3〜5 は成り立つ。2 の巻き込みは P0 の格子では起きなかった。「P0 結果」）

mermaid.js 11.17.2 の dagre の層（`dist/chunks/mermaid.core/chunk-2E4U76K2.mjs` の `adjustClustersAndEdges` / `extractor` / `getAnchorId`）と、
merman-render 0.8.0-alpha.6（`src/flowchart/layout.rs` の `external_connections` / `toggled_dir`）は同じ規則を持つ見込み:

1. 枠ごとに「**外とつながるか**」（`externalConnections`）を決める: どれかの線の両端の**ちょうど片方**が枠の子孫（中のノード・中の枠。**枠自身は含まない**）にあれば、外とつながる。
   - **枠そのものを指す線（`A --> 審査`）は、`審査` 自身にとっては外とつながる線ではない**（`審査` は自分の子孫ではない）。`審査` の**祖先**の枠にとっては、`審査` が子孫なので外とつながる線に数える（査読 1-3・2-1）
2. 線の端の付け替え（`getAnchorId`）: 端の枠が 1 で外とつながっていれば、その枠の中のノード 1 つ（`findNonClusterChild`）へ付け替えて引き、線を枠の縁で切る（`toCluster` / `fromCluster`）。
   その時、**付け替え先のノードの親の枠も外とつながる扱いになる**（入れ子なら内側の枠まで巻き込む）。外とつながらない枠を指す線は付け替えず、枠を丸ごと 1 つのノードにした後のそのノードへ引く
3. **外とつながる枠は、`direction` を書いても効かない**。その枠が置かれている側（図、または取り出された外側の枠）の向きで並ぶ（Mermaid の文書の flowchart の節にも同じ制約が書かれていたはず — 記憶で、まだ確かめていない）
4. **外とつながらない、中身のある枠**は別の図として取り出して並べる。向きは、`direction` があればそれ、**無ければ置かれている側の向きが `TB` なら `LR`、それ以外なら `TB`**
   （`let dir = graphSettings.rankdir === "TB" ? "LR" : "TB"`）。設定 `flowchart.inheritDir`（既定 false）を true にすると、無い時は図の向きを継ぐ
5. 図の向きの `TD` は `TB` にそろえる（flowDb の `setDirection`）が、**枠の中の `direction TD` は `TD` のまま**入る（字句の規則 `{ stmt: "dir", value: "TD" }`）。
   その枠の中の、向きの無い取り出される枠は、mermaid.js では `"TD" === "TB"` が偽なので `TB`、merman は `TD` も `TB` とみなすので `LR` — **実装の間で食い違う見込み**（P0 の 4）
6. 空の枠は描画で四角いノードになる（spec 15 D7）ので、中の向きは関係ない

**spec 15 の配置との食い違い**（今もある）: spec 15 の取り込み時の配置は、向きの無い枠の中も図の向きで並べる。
しかし**外とつながらない、向きの無い枠**は描画では逆向き（`TD` の図なら横）に並ぶので、そういう枠を持つ図はエディタと書き出しで並びが違う。spec 15 の受け入れ条件・P0 はこの点を測っていない。

## 決めること

### D1. データの形

- `ParsedMermaidSubgraph` に `direction?: SubgraphDirection` を足す（**書いた向き**。無ければ持たない = 書いていない）。
  図全体の `GraphType`（`TD` を既定にし、持たない時は `TD`）とは別の型にする — 枠では「書いていない」と「`TB` と書いた」が描画で違う（現況 4）ので、既定値で潰せない
- `SubgraphDirection` の値（**裁定 3**）。**型・生成器・GUI のメニュー（D7）の選択肢を同じ集合にする**（査読 1-1）:
  - 案 A（推奨）: `"TB" | "BT" | "LR" | "RL"`。取り込みで `TD` を `TB` にそろえ、生成器も `TB` と書く。メニューは「指定なし」・`TB`・`LR`・`RL`・`BT` —
    向きを読む所（接続点など）が `TD` を知らなくてよい。ただし `direction TD` の枠の中の、向きの無い取り出される枠は、往復で mermaid.js の描画が `TB` → `LR` に変わる（現況 5）。P0 の 4 でこれが実際に起きるかを測ってから決める
  - 案 B: `"TB" | "TD" | "BT" | "LR" | "RL"`（書いたまま残す）。メニューにも `TD` を足す
- 小文字（`direction lr`）は両方の実装で文法の誤り（P0 の 3）なので、取り込みに小文字は来ない。大文字にそろえる処理は要らない
- 裁定 3 の推奨は案 A（P0 の 3・4: 両方の実装とも `TD` を `TD` のまま持ち、その枠自身は `TB` と同じに描く。違いは中の向きの無い取り出される枠だけで、
  mermaid.js は `TB`、merman は `LR`。`TB` にそろえると両方とも `LR` になり、プレビュー（mermaid.js）と書き出し（merman）の食い違いが消える）
- 線（`ParsedMermaidEdge`）の型は変えない。`source` / `target` に**枠の ID も入りうる**とする（エディタでは枠のノードの ID）
- Rust の `FlowSubgraph` に `direction: Option<SubgraphDirection>`（serde で大文字の文字列。`None` は書かない）。文字列のままにすると小文字や知らない値も通るので enum にする（査読 1 の細部 1）
- data_contract: `EditorPayload.mapping.flowchart` の `edge_to_subgraph`・`subgraph_direction` の説明を「落とす」から「写す」へ書き換え、`dropped_constructs` から 2 つを外す（裁定 2 が案 B なら新しい construct を足す）。
  `ParsedMermaidData` の枠に `direction?`（査読 1 の細部 4）

### D2. 取り込み

- 線の端が枠の ID なら、落とさずに枠を端にした線にする（線の ID の規則は今のまま `{source}-{target}`、ぶつかれば番号）
- 枠の `dir` を `direction` に写す（D1 のそろえ方で）
- **枠と自分の子孫を結ぶ線**（`審査 --> C` で `C` が `審査` の中、`C --> 審査`、外枠と内枠、外枠と内枠の中のノード）の扱いは**裁定 2**。
  P0 の 1: 両方の実装とも誤りにせず、止まりもしないが、**描画では長さ 0 の線（`M x,y Z`）になって見えない**。それでいて枠を「外とつながる」扱いにし、枠の中の向きを変える（`S --> s1` で `S` の中が `LR` → `TB`）。
  **枠の自己ループ（`審査 --> 審査`）は別**で、両方の実装で枠の縁から出て戻る線として描かれ、枠を外とつながらせない
  - 案 A: そのまま写す — エディタでは線が見えるのに、書き出すと見えず、向きだけ変わる
  - **案 B（推奨）: 落として新しい construct `edge_into_own_subgraph` で数え、GUI でも作らせない**。枠の自己ループは写す（GUI でも作れる）。
    繋がせない判定は `isValidConnection`（子孫は `frame-edit.ts` の `descendantsOf` で根まで辿る）。
    **ノード・枠をドラッグして付け替えた結果そうなる線**（`A --> B` のある図で `B` を枠 `A` へ入れる, 査読 2-3）は、ドロップの時に確認を出し
    （「この移動で、枠『A』とその中を結ぶ線 1 本は描画されなくなるので消します」）、はいなら付け替えて線を消す、いいえならドラッグの前の位置へ戻す
- 枠と同じ ID のノードは作らない（spec 15 D1 のまま）。線の行き先はその枠になる

### D3. 生成器の書き方（往復が mermaid.js と merman の両方で戻ること）

- 枠に向きがあれば、`subgraph <ID>["<題>"]` の**次の行**に `direction <向き>` を書く（中のノード・子の枠より前。P0 の 3 で置き場所の違いが無いことを測る）
- 枠を指す線は、今の線と同じく**全部最後に外へ**書く。端の名前は枠の `variableName` を `getSafeVariableName` に通したもの（今のノードと同じ）
- **枠を指す線と向きの無い図の出力は一字一句変えない**（spec 15 までの出力と、初期図の突き合わせ: `__tests__/lib/desktop/doc-session.test.ts` の
  「エディタの初期図 (data_contract Document.initial_sources, spec 04 D4-2)」。初期図に枠は無い。spec 15 の枠の往復のテスト `round-trip-mermaid.test.ts` の期待も変えない, 査読 1 の細部 3）

### D4. エディタの枠の中の並びと接続点（**裁定 1**）

どの案でも、描画で効く向きを求める純粋な関数 `effectiveDirections`（下）は作る — 見出しの知らせに使う。案の違いは、**並べ（D5）と接続点（D6）がどちらの向きを読むか**。

- 案 A: **効く向き**で並べ、接続点も効く向き。取り込んだ図はエディタと描画で並びが合う。
  ただし**線を足す・消す・ノードを出し入れすると、効く向きが変わり接続点が縦横に跳ねる**（「枠を追加」した向きの無い枠は、外とつながらない間は `TD` の図で横、中のノードから外へ線を 1 本引くと縦。外すとまた横, 査読 2-5）
- **案 B（rev1 の推奨）: 書いた向き（無ければ置かれている側の向き）**で並べ、接続点もそれ。効く向きが違う時は見出しで知らせる。
  線の操作で接続点は跳ねない。取り込んだ図の並びが描画と違うのは「外とつながらない、向きの無い枠」（逆向きに描かれる）と「外とつながる、向きを書いた枠」（書いた向きが効かない）の 2 つで、どちらも見出しに出る。
  前者は利用者が向きを指定すれば描画と揃う（指定した向きは外とつながらない間は効く）
- 案 C: 向きは保存・生成器のためだけに持ち、並べ・接続点は図の向きのまま（spec 15 と同じ）。見出しに書いた向きを出す — 最も小さいが、`direction LR` を書いた枠がエディタでは縦に並ぶ

見出しの知らせ（案 A・B）。効く向き ≠ エディタの向きの時だけ出す:

- 外とつながる・向きを書いた枠: 「中のノードが枠の外とつながっているので、描画ではこの向き（LR）は効きません（TD で並びます）」— 「枠を指す線」ではなく「中のノードと外を結ぶ線」が理由だと書く（現況 1、査読 2-1）
- 外とつながらない・向きの無い枠（案 B）: 「描画では、この枠の中は横（LR）に並びます。向きを指定すると揃えられます」

`effectiveDirections(nodes, edges, direction)` の規則（**P0 の 4 で確定**。この規則を JS に写した予測を、両方の実装の描画で測った 520 点と突き合わせて食い違い 0。
rev1 の下書きにあった付け替えの巻き込みは、2 段の入れ子まで含めた格子で一度も起きなかったので外した。`TD` は裁定 3 の案 A で `TB` にそろえた後の値で読む）:

```text
desc(F)     = F の子孫（中のノード・中の枠。F は含まない）
external(F) = どれかの線 (s, t) で、s ∈ desc(F) と t ∈ desc(F) のちょうど片方が真
              ※ 端が枠そのもの X の線は、X の ID で数える: X 自身にとっては外の端、X の祖先にとっては中の端
              ※ 裁定 2 の案 B で落とした線（枠と自分の子孫）は線に無い。枠の自己ループは X ∉ desc(X) なので数えない
dir(根)     = 図の向き（TD は TB）
dir(F)      = F に中身が無い           → 無し（描画では四角いノード）
              external(F)              → dir(F の親の枠、無ければ根)
              F.direction がある        → F.direction
              それ以外                   → dir(F の親の枠、無ければ根) == "TB" ? "LR" : "TB"
接続点の向き: ノード・枠は「親の枠の dir、無ければ根の dir」（案 A の時）
```

- 線を足す・消す・出し入れで効く向きが変わった時、**並べ直さない・枠の大きさも変えない**（案 A では接続点だけが動く。案 B・C では接続点も動かず知らせだけが変わる）。
  取り込み時の配置で効く向き（または書いた向き）から枠の大きさを決めるのは、取り込みの時だけ（D5, 査読 1-2）

### D5. 取り込み時の配置

- `layoutNested` の向きを、図全体の 1 つから、**入れ物（図・枠）ごとの向き**にする（案 A なら効く向き、案 B なら書いた向き・無ければ置かれている側の向き、案 C なら今のまま）。
  **取り込みの時だけ**、その向きで並べ、中身の外接矩形から枠の大きさを決める（GUI の操作では並べ直さない, D4）
- 枠を指す線は、今の持ち上げ（`liftTo`）のまま数える（現況）。**枠と自分の子孫を結ぶ線は段組みに効かない**（現況、査読 2-7）— 裁定 2 が案 A でも配置では無視し、その子孫は入る線の無いものとして並べる
- 枠の無い図の配置は今と変わらない
- **保存済みの図**（spec 15 の版で保存したものを含む）を開き直した時は、`Document.layout` の位置と大きさを当てる（spec 15 D4）ので、並びは変わらない。
  新しい配置になるのは位置の無い枠・ノードだけ（MCP の `open_in_editor` の新しい図、`update_diagram` で増えたもの）。案 A では、開き直した図の接続点の向きは変わりうる（査読 2-9）

### D6. 接続点

- ノードの接続点は「**ノードが置かれている入れ物の向き**」（D4 の案で決まる向き）で決める。枠の外のノードは今のまま図の向き
- 枠にも入口（target）と出口（source）の接続点を付ける。位置は「**枠が置かれている入れ物の向き**」で決める（`TD` の図の直下の枠なら上の辺の中央と下の辺の中央）
- **向きの渡し方**（査読 2-6）: エディタが `nodes`・`edges`・図の向きから「ノード・枠の ID → 接続点の向き」の表を `useMemo` で作り、今の `DirectionContext`（図の向き 1 つ）に並べて表の Context を置く。
  ノード・枠は自分の ID で引く。**測り直しは各ノードの effect が自分の向きの変化で呼ぶ**（今の `useEffect(() => updateNodeInternals(id), [direction, …])` と同じ形。連鎖の仕組みは要らない。
  自前の `use-update-node-internals.ts`, failures #20）
- **見出し・つまみとの重なり**（査読 2-4）: `TD` なら入口が上の辺の中央 = 見出しの中、`LR` なら出口が右の辺の中央 = 選んだ時の右のつまみ（線）と重なる。
  P0 の 5 で、接続点を**見出し・つまみより後ろの DOM に置き、`pointer-events: all` を付けるだけ**（rev1 の案 i〜iii のどれも要らない）で、
  接続点の円（12px）の中心と上下左右 4px はどれも接続点が一番上、円から 10px 離れた右の辺ではつまみが受ける、と測れた。xyflow は線を引き始める時と離した時に `elementFromPoint` で接続点を探す（`@xyflow/system` の `onPointerDown`）ので、これで足りる見込み。
  **ドラッグで実際に線を引くことは P0 では確かめられなかった**（窓が描画されない状態で実物のマウスが使えず、JS で送ったイベントではノードどうしの対照の線も引けなかった）— P3 の画面で確かめる
- 枠の本体は押す操作を受けないまま（failures #25 の直しを崩さない）

### D7. GUI の編集

- **枠を指す線を作る**: ノード・枠の接続点から、別のノード・枠の接続点へドラッグ（今のノードどうしと同じ操作）。
  **線を引いて空いた所へ落とした時の解析を直す**（`parseConnectingNodeId` を、末尾の `-source` / `-target` だけを切る形にする。`-` を含む ID の今の不具合も直る。フォーク元の改善の別のコミットで Red → Green, 査読 2-2）。
  枠の出口から空いた所へ落とすと、今のノードと同じく新しいノードと線ができる。**新しいノードは、落とした所が枠の中でも図の直下にできる**（今の振る舞いのまま。スコープ外の項, 査読 1）
- 裁定 2 が案 B なら、枠と自分の子孫を結ぶ線は繋がせない（`isValidConnection`）。付け替えでそうなる線の扱いは D2 で決めたとおり
- **枠の向きを変える**: 枠の見出しに小さな向きのメニュー（`xs`、「指定なし」と D1 の値。図の `DirectionMenu` は `GraphType` 専用で `sm` なので、**枠用の部品を別に作る**。矢印のアイコンの表は共有する, 査読 2-8）。
  変えても位置は並べ直さない（図の向きと同じ）。案 A・B では、効く向きが違えば D4 の知らせを出す
- **枠を消す**: 枠につながる線は枠と一緒に消える（xyflow が消すノードにつながる線を足す。今の `planFrameDelete` の `removeEdges` が拾う）。確認の文に「枠につながる線 2 本も消えます」のように書く。
  中のノードにつながる線は今までどおり残る（spec 15 の裁定 3）
- **ID を変える**: 線はエディタの ID（xyflow の ID）でつながるので、枠の ID（`variableName`）を変えても線は外れない（P3 のテストで固定する）

### D8. 落とし続けるもの・知らせ方

- 裁定 2 が案 B なら、枠と自分の子孫を結ぶ線だけを `edge_into_own_subgraph` として落として数える（要約・行の印・MCP の `dropped`。文は「枠とその中を結ぶ線は描画されないので取り込みません」）
- LORELEI.md の既知の制約に、merman（書き出し）だけの描画の食い違いを足す: 外とつながる枠を外のノードから指す線が、枠の縁まで届かず短く描かれることがある（P0 の 1・追加。mermaid.js のプレビューでは届く。条件は絞り切れていない）
- `drop-warnings.ts` から、枠の中の `direction` の行と枠を指す線の行の印を外す（案 B の線だけ残す）
- LORELEI.md の既知の制約（`:91`）と MCP のツールの説明（`crates/lorelei_mcp/src/lib.rs:309・344`）から「サブグラフを指す線・サブグラフの中の direction」を外す
- ER 図のサブグラフ・それを指す関係は今のまま落とす（spec 11）

xyflow（P0 の 5）:

- 接続点は自分で `pointer-events: all` を持てば、本体が `none` の枠の上でも当たる。`TD` の上の辺の中央（見出しの中）でも、`LR` で枠を選んだ時の右の辺の中央（つまみの線の上）でも、`elementFromPoint` は接続点を返した（中心と上下左右 4px）。
  接続点から 10px 離れた右の辺ではつまみが受けた。どちらも、接続点を見出し・つまみより後ろの DOM に置いただけ（`z-index` も外へのずらしも無し）
- 線を引く処理は、引き始め（`clickedHandle`）と離した時（`handleBelow`）に `elementFromPoint` で接続点を探す（`@xyflow/system` 0.0.66 の `onPointerDown`）。上の結果から引ける見込みだが、
  **実物のドラッグは確かめられていない**: 窓が描画されない状態で実物のマウスの操作が通らず、JS で送ったマウス・ポインタのイベントではノードどうしの対照の線も引けなかった（送り方が足りない）。P3 の画面で確かめる
- 枠を端にした線の z の順（枠の下に隠れないか）は、線を作れないと見られないので P1 の画面に回す
- `parseConnectingNodeId` の不具合（現況）はコードで確かめた。画面での再現は P3 の Red のテストで示す
