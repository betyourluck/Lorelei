# Spec: サブグラフを指す線と、サブグラフの中の向きをエディタで扱う

**ID**: 16
**Date**: 2026-10-01
**Status**: **Draft rev0**（起票。査読と裁定 1〜3 を待つ。spec 15 P5 の持ち越し）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15 と同じく、**フォーク元の改善とデスクトップ・Rust・台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする

## Goal

spec 15 で枠（サブグラフ）はエディタに載ったが、落とし続けているものが 2 つある（spec 15 D6）:

1. **サブグラフを指す線**（`A --> 審査`・`審査 --> 通知`・`受付 --> 審査`）— 取り込みで落とし `edge_to_subgraph` として数える
2. **サブグラフの中の `direction`**（`subgraph 審査` の中の `direction LR`）— 取り込みで落とし `subgraph_direction` として数える

AI は段の流れを「枠から枠へ」の線で書き、枠の中を横に並べるために `direction` を書く。どちらもデスクトップで開くと最初の自動保存で消え、
`read_diagram` で読み戻しても戻らない。これを**取り込み・表示・保存・`read_diagram`・コード生成で落とさず、GUI で作れる・変えられる**ようにする。

あわせて、**エディタの枠の中の並びを、Mermaid の描画で効く向きに合わせるか**を決める（D4、裁定 1）。下の「現況」のとおり、
Mermaid の描画では枠の中の `direction` は**いつも効くわけではない**ので、書いた向きをそのまま並べに使うと、エディタと書き出した図の並びが食い違う。

## 裁定（未。査読の後に利用者が決める）

- **裁定 1（D4）**: エディタの枠の中の並びと接続点を、描画で効く向きに合わせるか — 推奨は案 A
- **裁定 2（D2）**: 枠と自分の中（子孫）を結ぶ線の扱い — P0 の結果を見て決める
- **裁定 3（D1）**: 枠の中の `direction TD` を `TB` にそろえるか — P0 の結果を見て決める

## 現況（2026-10-01、コードを読んで確かめた。描画の実測は P0）

### 取り込み（TS・Rust）

- TS: `features/flowchart/utils/from-mermaid.ts:100〜104` で、線の両端のどちらかがノードの ID に無い（= 枠の ID）時、`edge_to_subgraph` として落とす。
  `:120` で `dir` を持つ枠の数を `subgraph_direction` として数える。材料の `snapshot.subgraphs[].dir`（`components/ui/mermaid-snapshot.ts:37`）は**手元にある**
- Rust: `crates/lorelei_core/src/editor.rs:309〜312` で同じく落とし、`:223〜229` で `dir` が null でない枠を数える。`FlowSubgraph` に向きの欄は無い
- 枠と同じ ID のノードは作らない（spec 15 D1。mermaid.js も merman も、線が枠を指すとその ID のノードも作るため）。この規則はそのまま使える — 線の行き先を枠にすればよい
- インポートのダイアログの黄色の印（`features/flowchart/utils/drop-warnings.ts:78・84`）は、枠の中の `direction` の行と、枠の ID を端に持つ線の行に付く

### エディタ・生成器・配置

- 枠は `subgraphNode`（`components/node/subgraph-node.tsx`）。**接続点（`Handle`）を持たない**。本体は `pointer-events: none`（`FRAME_NODE_STYLE`、failures #25）で、見出し・つまみ・× だけが押す操作を受ける
- ノードの接続点は図全体の向きで決まる（`editable-node.tsx:31〜34` の `useDirection()` → `handlePositions`）。枠の中かどうかは見ない
- 生成器（`hooks/mermaid.ts:342〜360`）は線を全部最後に外へ書き、**両端のどちらかが枠の線は書かない**（「枠を指す線はエディタでは作れない」）。枠の中に `direction` の行は書かない
- 取り込み時の配置（`utils/nested-layout.ts` の `layoutNested`）は、図全体の向き 1 つで全部の枠の中を並べる。枠をまたぐ線は「同じ枠の中に並ぶ祖先」へ持ち上げる（`liftTo`）—
  `parentOf` に枠も入っているので、**線の端が枠でも持ち上げはそのまま効く**（端が枠そのものの時、その枠の中では無視され、外では枠として数える）
- 図の向きを変えても位置は並べ直さず、接続点だけが動く（spec 07。`flow-editor.tsx:655` の `onDirectionChange={setDirection}`）

### Mermaid の描画での枠の向き（ソースを読んだ。**P0 で描画を測って確かめる**）

mermaid.js 11.17.2 の dagre の層（`dist/chunks/mermaid.core/chunk-2E4U76K2.mjs` の `adjustClustersAndEdges` / `extractor`）と、
merman-render 0.8.0-alpha.6（`src/flowchart/layout.rs` の `external_connections` / `toggled_dir`）は同じ規則を持つ:

- 枠ごとに「**外とつながるか**」（`externalConnections`）を決める: どれかの線の両端の**ちょうど片方**が枠の子孫（中のノード・中の枠。枠自身は含まない）にあれば、外とつながる
- **枠を指す線**は、その枠が外とつながる時、枠の中のノード 1 つへ付け替えて引き（`findNonClusterChild`）、線の端を枠の縁で切る（`toCluster` / `fromCluster`）。
  付け替え先のノードの親の枠も外とつながる扱いになる。外とつながらない枠を指す線は、枠を丸ごと 1 つのノードにした後のそのノードへ引く
- **外とつながる枠は、`direction` を書いても効かない**。その枠が置かれている側（図、または取り出された外側の枠）の向きで並ぶ（Mermaid の文書の flowchart の節にも同じ制約が書かれていたはず — 記憶で、まだ確かめていない）
- **外とつながらない、中身のある枠**は別の図として取り出して並べる。向きは、`direction` があればそれ、**無ければ置かれている側の向きが `TB` なら `LR`、それ以外なら `TB`**
  （`let dir = graphSettings.rankdir === "TB" ? "LR" : "TB"`）。設定 `flowchart.inheritDir`（既定 false）を true にすると、無い時は図の向きを継ぐ
- 図の向きの `TD` は `TB` にそろえる（flowDb の `setDirection`）が、**枠の中の `direction TD` は `TD` のまま**入る（字句の規則 `{ stmt: "dir", value: "TD" }`）。
  その枠の中の、向きの無い取り出される枠は、mermaid.js では `"TD" === "TB"` が偽なので `TB`、merman は `TD` も `TB` とみなすので `LR` — **実装の間で食い違う見込み**（P0 の 4）

**spec 15 の配置との食い違い**（今もある）: spec 15 の取り込み時の配置は、向きの無い枠の中も図の向きで並べる。
しかし**外とつながらない、向きの無い枠**は描画では逆向き（`TD` の図なら横）に並ぶので、そういう枠を持つ図はエディタと書き出しで並びが違う。spec 15 の受け入れ条件・P0 はこの点を測っていない。

## 決めること

### D1. データの形

- `ParsedMermaidSubgraph` に `direction?: "TB" | "BT" | "LR" | "RL"` を足す（**書いた向き**。無ければ持たない = 書いていない）。
  図全体の `GraphType`（`TD` を既定にし、持たない時は `TD`）とは別の型にする — 枠では「書いていない」と「`TB` と書いた」が描画で違う（現況）ので、既定値で潰せない
- `TD` の扱い（**裁定 3**）: 案 A（推奨）取り込みで `TB` にそろえ、生成器も `TB` と書く — 型が 1 つ減り、ノードの接続点など向きを読む所が `TD` を知らなくてよい。
  ただし、`direction TD` の枠の中にある、向きの無い取り出される枠は、往復で mermaid.js の描画が `TB` → `LR` に変わる（現況の食い違い）。P0 の 4 でこれが実際に起きるかを測ってから決める /
  案 B: `TD` を残す（`direction?: "TB" | "TD" | …`）
- 線（`ParsedMermaidEdge`）の型は変えない。`source` / `target` に**枠の ID も入りうる**とする（エディタでは枠のノードの ID）
- Rust の `FlowSubgraph` に `direction: Option<String>`（無ければ書かない）。data_contract の `EditorPayload.mapping.flowchart`（`edge_to_subgraph`・`subgraph_direction` の行を落とす側から写す側へ）・`dropped_constructs` を直す

### D2. 取り込み

- 線の端が枠の ID なら、落とさずに枠を端にした線にする（線の ID の規則は今のまま `{source}-{target}`、ぶつかれば番号）
- 枠の `dir` を `direction` に写す（大文字にそろえる。P0 の 3 で小文字が通るかを測る）
- **枠と自分の子孫を結ぶ線**（`審査 --> C` で `C` が `審査` の中、`審査 --> 審査` の自己ループ、外枠と内枠）の扱いは**裁定 2**（P0 の 1 の結果で決める）:
  - 案 A: そのまま写す（描画で意味のある形に描かれるなら）
  - 案 B: 落として新しい construct（例 `edge_into_own_subgraph`）で数え、GUI でも繋がせない（描画が崩れる・誤りになるなら）
- 枠と同じ ID のノードは作らない（spec 15 D1 のまま）。線の行き先はその枠になる

### D3. 生成器の書き方（往復が mermaid.js と merman の両方で戻ること）

- 枠に向きがあれば、`subgraph <ID>["<題>"]` の**次の行**に `direction <向き>` を書く（中のノード・子の枠より前。P0 の 3 で置き場所の違いが無いことを測る）
- 枠を指す線は、今の線と同じく**全部最後に外へ**書く。端の名前は枠の `variableName` を `getSafeVariableName` に通したもの（今のノードと同じ）
- **枠を指す線と向きの無い図の出力は一字一句変えない**（spec 15 までの出力と、`initial_sources.flowchart` の突き合わせ, spec 04 D4-2）

### D4. エディタの枠の中の並びと接続点（**裁定 1**）

- **案 A（推奨）: 描画で効く向きに合わせる** — 現況の規則を TS の純粋な関数 1 つ（`effectiveDirections(nodes, edges, direction)`。枠ごとに効く向きを返す）に写し、
  取り込み時の配置（D5）と接続点（D6）がこれを読む。**書いた向き**（D1）は保存・生成器のためにそのまま持つ。
  書いた向きが効かない時（外とつながる枠）は、枠の見出しに「外とつながる線があるので、描画ではこの向き（LR）は効きません」と薄く書く。
  向きの無い取り出される枠が図と逆向きに描かれることも、効く向きとして同じく扱う（spec 15 の配置との食い違いも直る）。
  線を足す・消すと効く向きが変わりうる — その時は**接続点だけが動き、位置は並べ直さない**（図の向きを変えた時と同じ, spec 07）
- 案 B: 書いた向きだけで並べ・接続点を決める（無ければ図の向き = spec 15 のまま）。効かない時は見出しに知らせる — 規則を写さずに済むが、描画との食い違いが残る
- 案 C: 向きは保存・生成器のためだけに持ち、並べ・接続点は図の向きのまま（spec 15 と同じ）。見出しに書いた向きを出す — 最も小さいが、`direction LR` を書いた枠がエディタでは縦に並ぶ
- 案 A の規則の写しは、P0 の 4 の格子（mermaid.js と merman の描画の座標）を正解表にしたテストで固定する。両方の実装が食い違う所は mermaid.js（Web 版のプレビュー）と merman（書き出し）の
  どちらに合わせるかを P0 の後に決める（書き出しが実際の成果物なので merman を推す見込み）

### D5. 取り込み時の配置

- `layoutNested` の向きを、図全体の 1 つから、**入れ物（図・枠）ごとの向き**にする（案 A なら効く向き、案 B なら書いた向き、案 C なら今のまま）。
  枠の大きさは中身の外接矩形から決める（今のまま）ので、向きが変われば大きさも変わる
- 枠を指す線は、今の持ち上げ（`liftTo`）のまま数える（現況。端が枠そのものなら、その枠の外では枠として、その枠の中では無視される）
- 枠の無い図の配置は今と変わらない

### D6. 接続点

- ノードの接続点は「**ノードが置かれている入れ物の向き**」（D4 の案で決まる向き）で決める。枠の外のノードは今のまま図の向き
- 枠にも入口（target）と出口（source）の接続点を付ける。位置は「**枠が置かれている入れ物の向き**」で決める（`TD` の図の直下の枠なら上の辺の中央と下の辺の中央）
- 枠の本体は押す操作を受けないので、接続点は押す操作を受けるように戻す（つまみ・見出しと同じ, failures #25）。P0 の 5 で、本体が `pointer-events: none` のまま接続点から線を引けて、接続点へ落とせるかを画面で測る
- 向きが変わったら測り直す（今のノードと同じく自前の `use-update-node-internals.ts`, failures #20）

### D7. GUI の編集

- **枠を指す線を作る**: ノード・枠の接続点から、別のノード・枠の接続点へドラッグ（今のノードどうしと同じ操作）。枠の出口から空いた所へ落とすと、今のノードと同じく新しいノードと線ができる。
  裁定 2 が案 B なら、枠と自分の子孫を結ぶ線は繋がせない（xyflow の `isValidConnection`）
- **枠の向きを変える**: 枠の見出しに向きのメニュー（「指定なし」・`TB`・`LR`・`RL`・`BT`）。図の向きのメニュー（`DirectionMenu`, spec 07）と同じ部品を使えるか P1 で見る。
  変えても位置は並べ直さない（図の向きと同じ）。案 A なら、効かない時は D4 の知らせを出す
- **枠を消す**: 枠につながる線は枠と一緒に消える（xyflow が消すノードにつながる線を足す。今の `planFrameDelete` の `removeEdges` が拾う）。確認の文に「枠につながる線 2 本も消えます」のように書く。
  中のノードにつながる線は今までどおり残る（spec 15 の裁定 3）
- **ID を変える**: 線はエディタの ID（xyflow の ID）でつながるので、枠の ID（`variableName`）を変えても線は外れない（P1 のテストで固定する）

### D8. 落とし続けるもの・知らせ方

- 裁定 2 が案 B なら、枠と自分の子孫を結ぶ線だけを落として数える（要約・行の印・MCP の `dropped`）
- `drop-warnings.ts` から、枠の中の `direction` の行と枠を指す線の行の印を外す（案 B の線だけ残す）
- LORELEI.md の既知の制約（`:91`）と MCP のツールの説明（`crates/lorelei_mcp/src/lib.rs:309・344`）から「サブグラフを指す線・サブグラフの中の direction」を外す
- ER 図のサブグラフ・それを指す関係は今のまま落とす（spec 11）

## 受け入れ条件

1. 枠を指す線と枠の中の `direction` を持つフローチャートを MCP・インポートで開くと、線が枠につながって表示され、`dropped` に `edge_to_subgraph` / `subgraph_direction` が出ない（裁定 2 が案 B なら、枠と自分の中を結ぶ線だけが出る）
2. 開いた図を保存・`read_diagram`・コード生成・GUI の書き出しにかけると、枠を指す線と `direction` の行が残り、mermaid.js と merman の両方で同じ線と向きに読める
3. 枠を指す線も枠の中の向きも無い図の生成器の出力は一字一句変わらない。枠の無い図の取り込み時の配置も変わらない（初期図の突き合わせのテストが通る）
4. （裁定 1 が案 A の時）取り込み時の枠の中の並びと接続点の向きが、P0 の 4 の正解表どおり描画で効く向きになる。書いた向きが効かない枠は見出しで知らせる
5. GUI で、ノード・枠から枠へ、枠からノードへ線を引ける。枠の向きを変えられる。枠を消すと枠につながる線も消え、確認の文にそれが書かれる。その結果が 2 のとおりに書き出される
6. Web 版（GitHub Pages）のフローチャートのエディタで 1（インポート）・2（コード生成まで）・5 ができる（デスクトップ専用の変更を含まない）

## スコープ外

- ER 図のサブグラフ・それを指す関係（spec 11 のまま）
- `classDef` / `class` / `style` / `linkStyle`（枠の色を含む）
- 設定 `flowchart.inheritDir`（frontmatter・`%%{init}%%` の設定は今も取り込まない）
- 向きを変えた時に位置を並べ直す操作（図の向きと同じく、接続点だけを動かす）
- 線の接続点から空いた所へ落として作った新しいノードを、落とした所の枠に入れること（今は枠の中に落としても図の直下にできる。spec 15 からの振る舞い。要るなら別に起票）
- 選んだノードを「枠で囲む」操作（spec 15 裁定 2 のまま）
