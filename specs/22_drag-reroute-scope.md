## Goal

spec 19・21 で残した候補「大きな図の線の多いノードのドラッグを軽くする」（「線の多い」は当たっていなかった。下調べの 2）。

- spec 21 の P0・P1 のブラウザの測り（Browser pane を表示した状態）で、枠の無い大きな図（ノード 100・線 150）の n57 をドラッグすると、ドラッグ中の 1 回の計算の中央値が **37〜49ms**
  （spec 19 P1 は窓が隠れた環境で 27〜36ms）。spec 19 D4 の基準（33ms）を今のコードで超えている（spec 21 D6 で、spec 21 の基準は「増分」に改めて先送りした）
- 計算は主スレッドで走るので、その間は画面が止まる。8ms を超えた計算の後は、次の計算をその時間の 2 倍遅らせる（spec 17 P1 で足した間引き）ので、
  今のコードの n57 では**回した線が 110〜150ms ほどの間隔でしか付いてこない**見込み（37〜49ms の計算 + その 2 倍の待ち。式から求めただけで、間隔は測っていない）

**これは利用者からの苦情ではなく、測りで基準を超えている件**である。spec 17 P2 で利用者は大きな図のドラッグを「問題なし」と言い、spec 19・21 の P2 でも配布ビルドでドラッグして通した。
図が大きくなるほど（回る線と、その外接矩形が覆う広さが増えるほど）重くなる見込みなので、ここで軽くしておく（利用者が候補 2 として選んだ, 2026-10-13）。

rev1 までは、ドラッグ中に探し直す線を絞る案（D1 の案 A）を推していた。P0 で次の 3 つが分かった（P0 結果）:
**経路の探索そのものを速くする案（案 B）だけで足り、出す道も今と同じ**・**手を離した時の全部の探し直しが実物で一度も走っていなかった**（failures #38）・
**大きな図のドラッグの重さの大半は描き直し**（経路の計算を止めてもフレームの間隔は 83ms）。
rev2 では、**探索を速くし（出す道は変えない）、手を離した時の全部の探し直しを実物で効かせる**。描き直しは次の spec にする。

変えるのはエディタの線の描き方（表示）だけ。**保存ファイル・コード生成・`read_diagram`・書き出しの出力**には何も足さない・変えない（spec 17・19・21 と同じ）。
`routeEdges` を呼ぶのは `use-edge-routes.ts` だけで（2026-10-13 に grep で確かめた）、結果は線の部品の表示にしか使わない。

## 現況（2026-10-13、コードを読んで確かめた。数は下の「起票前の下調べ」）

- **計算の予約**（`features/flowchart/hooks/use-edge-routes.ts` の `useEdgeRouting`）: xyflow のストアの知らせを 1 フレームに 1 回にまとめて `run` を呼ぶ。
  ドラッグ中に前の `run` が 8ms（`SLOW_RUN_MS`）を超えた時は、次をその時間の 2 倍遅らせる（`setTimeout`）。**ドラッグを終えた時は、形が変わっていなくても全部を探し直す**
  （とコードは書いているが、**実物では走っていなかった**。手を離してもノードの `dragging` が残るため。P0 で見つけた。failures #38）
- **矩形は絶対座標**（`boxesOf` が xyflow の `positionAbsolute` を使う）。枠を動かすと、中のノード・枠の矩形も変わる
- **使い回す線**（同じファイルの `reusableEdges`、spec 17 D4 の案 iii）: ドラッグ中は、次を全部満たす線を、前の探索の結果（`cache`）から使い回す。
  ① 線の入力（端の名前・接続点・ボタンの幅・ずれ）が前と同じ ② 端のノードが動いていない
  ③ **動いたノード・枠の今の矩形と前の矩形のどれも、その線の範囲にかからない**。範囲は、回した線なら前の折れ線の、回していない線なら今の曲線の**外接矩形を 24px（2 MARGIN）広げたもの**
- `routeEdges`（`features/flowchart/utils/edge-route.ts`）は、使い回さない線ごとに `needsRoute`（回すか）→ 回すなら `routeOne`（突き出し・`nearby` で避けるものを絞る・`search` の A*）。
  使い回すかに関わらず、**全部の線**に `viewOf`（線ごとに全部の矩形を振り分ける）、回した線の全部に `separate`（重なる線分を離す）と `placeButton`、
  回さない線の全部に `placeCurveButtons`（spec 21）を毎回かける
- **`cache` に入るのは離す前の道**（`routeOne` の結果の写し。`separate` の前）。使い回した線も、その写しから始めて毎回 `separate` をかけ直す
- **`needsRoute` が見るのは、今の曲線と回さない時のボタンを囲む矩形（`reach`）に重なる矩形だけ**。その中の枠（端の祖先でないもの・端である枠）に曲線かボタンがかかるか、
  ノード（端でも端の祖先でもないもの）を曲線が貫くか・ボタンが縦横とも 12px 以上かかるかで決まる。`reach` は線の入力だけで決まる
- **`routeOne` が避けるもの**は、障害物（どちらの端も中にいないノード・枠）と端そのものを MARGIN 広げた矩形と、**通れる枠（端の祖先の枠）は見出しの帯だけ**を MARGIN 広げた矩形
- **`separate` は離した線分を、障害物の内側に入れず、MARGIN の半分より近づけない**（離した線分と両隣を、広げない矩形で `pathHits`、離した線分を MARGIN/2 広げた矩形で `pathHits`）。
  したがって**表示する折れ線の保証は「障害物の内側を通らない」**で、MARGIN 広げた矩形ではない
- **n57 に付いている線は 5 本**（`n48 → n57`・`n49 → n57`・`n57 → n53`・`n57 → n32`・`n57 → n40`）。spec 19・21 と CLAUDE.md の「線の多いノード」は当たっていない（下調べの 2）

## 言葉の定義

```text
動いたもの          = ドラッグ中の 1 回で、前の回から矩形（絶対座標・大きさ・親）の変わったノード・枠と、消えたノード・枠。
                      枠を動かすと中のノード・枠も動いたものに入る（矩形が絶対座標なので）。判定は線ごとに「動いたもののどれか」を見るだけなので、
                      枠と中のものが両方入っても、同じ線を 2 回探すことはない
今の矩形 / 前の矩形 = 動いたものの、この回 / 前の回の矩形（新しく出たものは前の矩形が無く、消えたものは今の矩形が無い）
前の道(線)          = cache に残った、その線の前の回の結果（回した線は離す前の折れ線、回していない線は null）
届く所(線)          = 今の曲線と、回さない時のボタンを囲む矩形（needsRoute が見る範囲 reach。線の入力だけで決まる）
回す要(線)          = 今の矩形の全部で見た needsRoute（spec 19 裁定 1・2 の規則のまま）
避ける形(もの, 線)  = その線にとって、もの が障害物なら矩形、通れる枠（端の祖先の枠）なら見出しの帯（routeOne の避けるものと同じ形）
重なる(矩形, 矩形)  = 2 つの矩形の内側が交わる（edge-route.ts の rectsOverlap）
かかる(形, 道)      = 形を MARGIN 広げた矩形の内側を、道の線分が通る（edge-route.ts の pathHits(道, grow(形, MARGIN))）。形は広げる前のものを書く
探し直す線          = この回に探索（routeOne）を走らせる線
```

## 決めること

### D1. 何で軽くするか（**裁定 = 案 B だけ**）

rev2: P0 の後、推奨を案 B だけに改め、利用者が裁定した（冒頭の「裁定」）。下の案 A・案 B の説明は rev1 のまま残す。


- **案 A（推奨）: 使い回しの判定を細かくする** — ドラッグ中は、線ごとに次の順で決める（下調べの 3）:
  1. 線の入力が前の回と違う線・前の回に無かった線・**端が動いたものに入る線** → 今と同じく、回す要を求め、要があれば探す
  2. それ以外の線で、**動いたもののどれかの今の矩形か前の矩形が、届く所に重なる** → 回す要を求め直す。
     重ならなければ、回す要は前の回と同じ（前の道が折れ線なら要あり、null なら要なし）
  3. 回す要が無い → 曲線のまま・曲線に戻す（探索は走らない）
  4. 回す要があり、前の道が null → 探す
  5. 回す要があり、前の道が折れ線 → **動いたもののどれかの、今の矩形での避ける形が、前の道にかかる**なら探し直す。かからなければ前の道を使う

  - **2 で回す要が変わらないと言える理由**: `needsRoute` が見るのは届く所に重なる矩形だけで、届く所は線の入力だけで決まる（1 で入力が変わった線は除いてある）。
    届く所に重なる矩形の集まりとその矩形が前の回と同じなら、答えも同じ。変わりうるのは、動いたものが届く所に入った・出た・中で動いた時だけで、そのどれでも今か前の矩形が届く所に重なる。
    線ごとの振り分け（障害物・端・通れる枠）は端の祖先で決まり、祖先が変わるのは手を離した時（`onNodeDragStop` の `applyDrop` による枠への出し入れ）で、その時は全部を探し直す（D3）。下調べで、食い違いは全部の歩で 0
  - **5 で今の矩形だけを見て、前の矩形を見ない理由**: 前の道は、前の回の避けるもの（動いたものの前の位置を含む）にかからない道として探したので、
    動いたものがどいても道は成り立つ（遠回りになるだけ）。どいて回す要が無くなった線は 2・3 で曲線に戻る
  - **5 で避ける形を使う理由**: 通れる枠（端の祖先の枠）の中を通る道は、枠の矩形には必ずかかる。`routeOne` と同じく見出しの帯だけを見ないと、
    枠を動かすたびに枠の中の線を全部探し直す（査読 2-4）
  - **使い回した道（離す前）は、その回の位置でも探索と同じ条件**（避けるものを MARGIN 広げた矩形にかからない）を満たす: 前の回で満たしていて、変わったのは動いたものだけで、
    5 で動いたもののどれかにかかる道は探し直すので。`separate` は今と同じく、使い回した道にも毎回かけ直すので、**表示する折れ線の保証は全部の計算と同じ**（障害物の内側を通らない）。
    使い回した線を `separate` から外すことはしない（外すと、手を離した後の全部の計算と離し方が変わる）
  - 下調べで、重かった場面（37〜53ms）のノードのドラッグの中央値は 5〜14ms に、探索の回数は 22〜40 回から 3〜7 回になった。枠 F10 のドラッグは 34〜37ms → 22〜24ms
  - **代わりに変わること**: 回した線の道は、障害物がどいても（まだ回す要がある限り）ドラッグ中は前の道のまま残る（遠回りのまま）。今は、外接矩形にかかるだけで探し直すので、道が縮む。
    手を離すと全部を探し直すので、ドラッグ中の最後の回から手を離した後へ、道が変わる線がある（D3）
- 案 B: 探索（`search`）そのものを速くする — 格子の作り方（行ごとの `filter`・`some`）、`moves` の配列と重みの組の毎回の確保、`dist` の毎回の確保と `fill` を減らす。
  振る舞いは変わらない。何倍になるかは**見込みも測っていない**（P0 で写しを測る）。案 A と重ねられる。枠のドラッグ（1 の線が多い）に効くのはこちら
- 案 C: 1 回の時間の上限（例 8ms）を決め、探し直す線を数フレームに分ける（動いたノードの線を先に）— 主スレッドの止まりは上限で抑えられるが、線が数フレーム遅れて付いてくる。
  案 A の後も重い図が残る時の次の手
- 案 D: ドラッグ中は端が動いた線だけを探し直し、ほかは手を離すまで前の道のまま — 一番軽いが、動いたノードの上を古い線が通る（spec 19 で直した「線がノードの後ろに隠れる」がドラッグ中に戻る）
- 案 E: 探索を Web Worker へ移す — 主スレッドは止まらないが、結果が非同期になり、作りが大きい（Web 版とデスクトップの両方の読み込み、ストアの受け渡し）。線の遅れは残る

推す理由: 下調べで、重さの元は探索の回数で、その大半が**動いたものと関わらない線の探し直し**だった。案 A はその無駄だけを削り、ドラッグ中の線の正しさ
（回す要どおりに回す・障害物の内側を通らない）は今と同じに保つ。案 B は振る舞いを変えない利点があるが、効き目を測っていないので、P0 で案 A の後に残る時間を見てから決める。

### D2. 速さの基準（**裁定 = 本番と同じ組み立てで中央値 16ms 以下。推奨どおり** → **rev3 で改めた**: 冒頭の「裁定」と受け入れ条件 1）

- **基準（仮。P0 の後に利用者と決める）**: ノード n38・n57・n68 のドラッグで、**ドラッグ中の 1 回の中央値が 16ms 以下**（60Hz の 1 フレーム）。最大は記録するが基準に入れない
  - どの位置で満たすかを P0 の後に決める: (i) 2 つの図の取り込み直後と保存された位置の 4 通り全部（推奨。下調べの保存された位置では 5〜14ms） (ii) 取り込み直後だけ (iii) 16ms の代わりに「今のコードの半分以下」
  - **枠のドラッグは記録するが基準に入れない**（下調べの F10 は 22〜24ms。中のノードの線は端が動くので、案 A では減らない。案 B を採るかの材料にする）
- **全部の計算 1 回は増分で見る**: 今のコードと交互に測り、中央値の増分が 3ms 以下（spec 21 D6 と同じ形）。案 A はドラッグしていない時の計算を変えない（使い回さない）。
  100ms の絶対の基準は、下調べで今のコードでも超える場面があり、全部の計算はこの spec のスコープ外なので使わない（査読 2-1）
- 測り方は spec 19 D4・spec 21 D6 と同じ（ブラウザ、Web 版 `next dev`、**Browser pane を表示した状態**、合成のマウスの事件で 30 歩、往きと帰り、今のコードと交互に）

### D3. 手を離した時（**裁定 = 案 A。failures #38 の穴を直して効かせる**）

- **案 A（推奨）: 今のまま、手を離したら全部を探し直す** — 手を離した後の線とボタンは今のコードと同じ（受け入れ条件 4）。
  案 A のドラッグ中に遠回りのまま残った線は、手を離した時に縮む（ドラッグ中の最後の回から、手を離した後へ道が変わる）
- 案 B: 手を離しても探し直さず、ドラッグ中の道を残す — 手を離した時に線は跳ねないが、遠回りの線が残り、開き直すと（全部の計算で）道が変わる。保存しない表示なので、同じ図が開くたびに違って見える

下調べでは、ドラッグ中の最後の回から手を離した後へ道が変わった線は、今のコードで 0〜12 本、案 A で 0〜24 本。P0 でブラウザで、本数と変わった大きさ（道のりの差）を今と案 A で数え、変わりの大きい場面を撮る（利用者がこれを見て決める）。

### D4. 間引き（`SLOW_RUN_MS` と 2 倍の待ち）（**裁定 = 案 B（今のまま）。推奨どおり**）

rev2: P0 で閾値を変えても差が見えなかったので、推奨を案 B に改めた（P0 結果の 4）。


- **案 A（推奨）: D2 の基準を満たしたら、閾値を 16ms に上げる** — 今の閾値（8ms）のままだと、案 A で中央値が 8〜16ms の場面（下調べで n57 は 10〜14ms）でも間引きが効き、
  案 A の後の線は 30〜40ms 間隔でしか付いてこない見込み（計算 + その 2 倍の待ち）。D2 の 16ms（1 フレーム）と揃えると、1 フレームに収まる計算は毎フレーム走る。
  閾値を超える重い回（枠のドラッグなど）は今と同じく間引く。P0 で、閾値 8ms と 16ms の時の、ノードの動きのフレームの間隔と線の付いてくる間隔を測って確かめる
- 案 B: 今のまま（8ms・2 倍）

## スコープ外

- 探索の規則（道のり + 曲がりの重み、MARGIN、格子）を変えること。案 B は確保と作り方だけで、出る道は変えない
- 使い回しの判定を細かくすること（D1 の案 A。P0 で、案 B に重ねても線の付いてくる間隔とフレームの間隔が変わらず、手を離した時に道が大きく変わる場面が出た）
- **ドラッグ中の描き直しを軽くすること**（P0 結果の 2。大きな図のドラッグの重さの大半。次の spec の候補）
- 計算を主スレッドの外へ移すこと（D1 の案 E）・時間の上限で分けること（案 C）。案 A の後も重い図（枠のドラッグなど）が残れば次の spec の候補
- 全部の計算 1 回（取り込み直後・手を離した時）を速くすること（受け入れ条件 1 は増分だけを見る）
- 回した線の通り道を手で動かす（候補 ⑥）・回さない曲線が端の祖先の枠の見出しを通る形（候補 ⑦ の前半）・ボタンの大きさを実物で測る・両端のノードを貫く逆向きの線
- 端のノードがほかのノードに重なった時に、障害物の内側を通る線（今のコードと同じ）
- xyflow の線とノードの描き直しの時間（React の描画）。この spec は `run` の時間だけを基準にする（フレームの間隔は記録する）
