# Spec: 大きな図のドラッグを軽くする（ドラッグ中に探し直す線を絞る）

**ID**: 22
**Date**: 2026-10-13
**Status**: Draft（rev0。起票。査読待ち）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15〜21 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 19・21 で残した候補「大きな図の線の多いノードのドラッグを軽くする」。

- spec 21 の P0・P1 のブラウザの測り（Browser pane を表示した状態）で、枠の無い大きな図（ノード 100・線 150）の n57 をドラッグすると、ドラッグ中の 1 回の計算の中央値が **37〜49ms**
  （spec 19 P1 は窓が隠れた環境で 27〜36ms）。spec 19 D4 の基準（33ms）を今のコードで超えている（spec 21 D6 で、spec 21 の基準は「増分」に改めて先送りした）
- 計算は主スレッドで走るので、その間は画面が止まる。8ms を超えた計算の後は、次の計算をその時間の 2 倍遅らせる（spec 17 D4 の間引き）ので、
  n57 では**回した線が 110〜150ms ほどの間隔でしか付いてこない**見込み（37〜49ms の計算 + その 2 倍の待ち。式から求めただけで、間隔は測っていない）

**これは利用者からの苦情ではなく、測りで基準を超えている件**である。spec 17 P2 で利用者は大きな図のドラッグを「問題なし」と言い、spec 19・21 の P2 でも配布ビルドでドラッグして通した。
図が大きくなるほど（回る線と、その外接矩形が覆う広さが増えるほど）重くなる見込みなので、ここで軽くしておく（利用者が候補 2 として選んだ, 2026-10-13）。

これを、**ドラッグ中に探し直す線を、動いたものと本当に関わる線だけに絞る**ことで軽くする。

変えるのはエディタの線の描き方（表示）だけ。**保存ファイル・コード生成・`read_diagram`・書き出しの出力**には何も足さない・変えない（spec 17・19・21 と同じ）。

## 現況（2026-10-13、コードを読んで確かめた。数は下の「起票前の下調べ」）

- **計算の予約**（`features/flowchart/hooks/use-edge-routes.ts` の `useEdgeRouting`）: xyflow のストアの知らせを 1 フレームに 1 回にまとめて `run` を呼ぶ。
  ドラッグ中に前の `run` が 8ms（`SLOW_RUN_MS`）を超えた時は、次をその時間の 2 倍遅らせる（`setTimeout`）。**ドラッグを終えた時は、形が変わっていなくても全部を探し直す**
- **使い回す線**（同じファイルの `reusableEdges`、spec 17 D4 の案 iii）: ドラッグ中は、次を全部満たす線を、前の探索の結果（`cache`）から使い回す。
  ① 線の入力（端の名前・接続点・ボタンの幅・ずれ）が前と同じ ② 端のノードが動いていない
  ③ **動いたノード・枠の今の矩形と前の矩形のどれも、その線の範囲にかからない**。範囲は、回した線なら前の折れ線の、回していない線なら今の曲線の**外接矩形を 24px（2 MARGIN）広げたもの**
- `routeEdges`（`features/flowchart/utils/edge-route.ts`）は、使い回さない線ごとに `needsRoute`（回すか）→ 回すなら `routeOne`（突き出し・`nearby` で避けるものを絞る・`search` の A*）。
  使い回すかに関わらず、**全部の線**に `viewOf`（線ごとに全部の矩形を振り分ける）、回した線の全部に `separate`（重なる線分を離す）と `placeButton`、
  回さない線の全部に `placeCurveButtons`（spec 21）を毎回かける
- **n57 に付いている線は 5 本**（`n48 → n57`・`n49 → n57`・`n57 → n53`・`n57 → n32`・`n57 → n40`）。spec 19・21 と CLAUDE.md の「線の多いノード」は当たっていない（下調べの 2）

### 2. n57 で 27 本を探し直す理由

n57 の線は 5 本なのに、1 歩ごとに約 27 本を探し直していた。回した線（枠なしで 57 本）の多くは図の両脇へ回る長い道で、その**外接矩形が図の大部分を覆う**。
動いたノードがその矩形に入るだけで、折れ線から遠くても使い回せない。n57 は図の中ほどにあるので、多くの回した線の外接矩形の中にいる。

### 3. 判定を細かくした写し（下の D1 の案 A）

使い回せない線を、次の 4 つに絞った写しで同じ測りをした（探索の中身は今のまま）:

### 下調べの限り

- vitest（Node）の数で、ブラウザの数ではない。枠なしの n57 は前のブラウザの測り（spec 21 P1: 38〜49ms）と近いが、**枠ありは前のブラウザの測り（14〜27ms）より大きい**。
  前のブラウザは取り込み直後の位置、今回は保存された位置（利用者が動かした後）で、枠の接続点も近似している。どちらが効いているかは確かめていない → P0 でブラウザで測る
- 写しは「使い回した線の道が、動いたものに対して成り立つか」を見ただけで、手を離した時の全部の探し直しとどれだけ違うか（下の D3）は数えていない

## 言葉の定義

```text
動いたもの        = ドラッグ中の 1 回で、前の回から矩形の変わったノード・枠（枠を動かすと中のノードも動いたものに入る）
今の矩形 / 前の矩形 = 動いたものの、この回 / 前の回の矩形
前の道(線)        = cache に残った、その線の前の探索の結果（回した線は折れ線、回していない線は null）
範囲(線)          = 前の道の折れ線（null なら今の曲線）の外接矩形を 2 MARGIN 広げたもの（今の reusableEdges と同じ）
かかる(矩形, 道)  = 矩形を MARGIN 広げたものの内側を、道の線分が通る（edge-route.ts の pathHits）
回す要(線)        = 今の矩形の全部で見た needsRoute（spec 19 裁定 1・2 の規則のまま）
探し直す線        = この回に探索を走らせうる線（使い回さない線）
```

## 決めること

### D1. 何で軽くするか

- **案 A（推奨）: 使い回しの判定を細かくする** — ドラッグ中に使い回さないのは次の線だけ（下調べの 3）:
  1. 線の入力が前と違う線、端が動いた線（今と同じ）
  2. 前の道が折れ線の線で、動いたものの**今の矩形が前の道にかかる**線 → 探し直す
  3. 前の道が折れ線の線で、動いたものの**前の矩形が範囲にかかり**、**回す要が無くなった**線 → 曲線に戻す（探索は走らない）
  4. 前の道が null の線で、動いたものの今の矩形が範囲にかかり、**回す要が出た**線 → 探す

  ほかの線は前の道をそのまま使う。**使い回した道は、ドラッグ中も探索と同じ条件（避けるものを MARGIN 広げた矩形を通らない）を満たす**（前の回で満たしていて、変わったのは動いたものだけで、2 でかかるものは探し直すので）。
  下調べで、重かった場面（41〜72ms）のドラッグ中の 1 回の中央値は 5〜14ms に、探索の回数は 22〜40 回から 3〜7 回になった
  - **代わりに変わること**: 回した線の道は、障害物がどいても（まだ回す要がある限り）ドラッグ中は前の道のまま残る（遠回りのまま）。今は、範囲にかかるだけで探し直すので、道が縮む。
    手を離すと全部を探し直すので、**手を離した時に道が今より大きく変わりうる**（D3）
- 案 B: 探索（`search`）そのものを速くする — 格子の作り方（行ごとの `filter`・`some`）、`moves` の配列と重みの組の毎回の確保、`dist` の毎回の確保と `fill` を減らす。
  振る舞いは変わらない。何倍になるかは**見込みも測っていない**（P0 で写しを測る）。案 A と重ねられる
- 案 C: 1 回の時間の上限（例 8ms）を決め、探し直す線を数フレームに分ける（動いたノードの線を先に）— 主スレッドの止まりは上限で抑えられるが、線が数フレーム遅れて付いてくる。
  案 A の後も重い図が残る時の次の手
- 案 D: ドラッグ中は端が動いた線だけを探し直し、ほかは手を離すまで前の道のまま — 一番軽いが、動いたノードの上を古い線が通る（spec 19 で直した「線がノードの後ろに隠れる」がドラッグ中に戻る）
- 案 E: 探索を Web Worker へ移す — 主スレッドは止まらないが、結果が非同期になり、作りが大きい（Web 版とデスクトップの両方の読み込み、ストアの受け渡し）。線の遅れは残る

推す理由: 下調べで、重さの元は探索の回数で、その大半が**動いたものと関わらない線の探し直し**だった。案 A はその無駄だけを削り、ドラッグ中の線の道の正しさ（障害物を通らない）は保つ。
案 B は振る舞いを変えない利点があるが、効き目を測っていないので、P0 で案 A の後に残る時間を見てから決める。

### D2. 速さの基準

- **基準（仮。P0 の後に利用者と決める）**: 2 つの図（枠あり・枠なし）の取り込み直後と保存された位置で、n38・n57・n68 の**ドラッグ中の 1 回の中央値が 16ms 以下**（60Hz の 1 フレーム）。
  全部の計算 1 回が 100ms 以下（spec 19 D4 のまま）
- 測り方は spec 19 D4・spec 21 D6 と同じ（ブラウザ、Web 版 `next dev`、**Browser pane を表示した状態**、合成のマウスの事件で 30 歩、往きと帰り、今のコードと交互に）
- 案: 中央値でなく最大や 95 パーセンタイルも見るか — 間引き（D4）があるので、1 回の最大はドラッグの止まりの最大になる。P0 で中央値と並べて記録し、基準に入れるかは利用者と決める

### D3. 手を離した時

- **案 A（推奨）: 今のまま、手を離したら全部を探し直す** — 手を離した後の線とボタンは今と同じ（受け入れ条件 4）。D1 の案 A では、ドラッグ中に遠回りのまま残った線が、手を離した時に縮む
- 案 B: 手を離しても探し直さず、ドラッグ中の道を残す — 手を離した時に線は跳ねないが、遠回りの線が残り、開き直すと（全部の計算で）道が変わる。保存しない表示なので、同じ図が開くたびに違って見える

P0 で、手を離した時に道が変わった線の本数を、今と案 A で数え、画面で見る（利用者がこれを見て決める）。

### D4. 間引き（`SLOW_RUN_MS` と 2 倍の待ち）

- **案 A（推奨）: P0 の後に決める** — 案 A で中央値が 8ms を超える図（下調べで n57 は 10〜14ms）では、今の間引きが効いて、線が 30〜40ms 間隔で付いてくる見込み（計算 + その 2 倍の待ち）。
  間引きをやめると主スレッドが毎フレーム 10ms 余り止まる。P0 で、間引きの閾値を 8ms のままと 16ms にした時の、ノードの動き（フレームの間隔）と線の付いてくる間隔を測る
- 案 B: 今のまま（8ms・2 倍）

### D5. 判定の置き場所

- **案 A（推奨）: 判定を `edge-route.ts` へ移す** — 2〜4 の判定は `needsRoute`・`viewOf`・`pathHits` を使う（どれも `edge-route.ts` の中の関数で、今は書き出していない）。
  `routeEdges` が動いたものの今と前の矩形を受け取り、使い回すかを自分で決める（`RouteOptions` に足す）。フックは動いたものを求めて渡すだけにする。
  使い回した線にも `viewOf` は要る（`separate` と `placeButton` が使う）ので、判定と同じ `viewOf` を使い回せる
- 案 B: フックの `reusableEdges` のまま、`edge-route.ts` から 3 つの関数を書き出す — 1 つの規則（回すか）がフックと `edge-route.ts` の両方から呼ばれる

## 受け入れ条件

1. 2 つの図（枠あり・枠なし）の取り込み直後と保存された位置で、n38・n57・n68 のドラッグ中の 1 回の中央値が D2 の基準以下（ブラウザ、今のコードと交互に測る）。全部の計算 1 回が 100ms 以下
2. ドラッグ中のどの回も、回した線の表示する折れ線は、その線の障害物（どちらの端も中にいないノード・枠）の内側を通らない（使い回した道を含む。今の全部の計算と同じ保証。
   MARGIN 広げた矩形でないのは、`separate` が線分を障害物から MARGIN の半分まで寄せるため）。使い回した道（離す前）は、動いたものを MARGIN 広げた矩形にかからない
3. ドラッグ中に回す要が無くなった線は、その回に曲線へ戻る。回す要が出た線は、その回に回る（spec 17 の「どくと曲線に戻る」・spec 19 の「ノードを貫く線を回す」がドラッグ中も成り立つ）
4. 手を離した後の線の道とボタンの位置は、今のコードの全部の計算と同じ（D3 の案 A の時）
5. 保存ファイル・コード生成・`read_diagram`・書き出しの出力は変わらない
6. Web 版（GitHub Pages）のフローチャートのエディタで 1〜4 が成り立つ（デスクトップ専用の変更を含まない）

## スコープ外

- 探索の規則（道のり + 曲がりの重み、MARGIN、格子）を変えること。案 B は確保と作り方だけで、出る道は変えない
- 計算を主スレッドの外へ移すこと（D1 の案 E）・時間の上限で分けること（案 C）。案 A の後も重い図が残れば次の spec の候補
- 全部の計算 1 回（取り込み直後・手を離した時）を速くすること
- 回した線の通り道を手で動かす（候補 ⑥）・回さない曲線が端の祖先の枠の見出しを通る形（候補 ⑦ の前半）・ボタンの大きさを実物で測る・両端のノードを貫く逆向きの線
- xyflow の線とノードの描き直しの時間（React の描画）。この spec は `run` の時間だけを測る
