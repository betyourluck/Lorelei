# Spec: 枠をまたぐ線を、途中の枠の外へ回す

**ID**: 17
**Date**: 2026-10-03
**Status**: Draft（rev0。査読と P0 の前）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15・16 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 16 で枠（サブグラフ）を指す線が描けるようになったが、**枠をまたいで戻る線（下の枠から上のノードへ）が、間にある枠の真ん中を貫いて描かれる**
（spec 16 P2「見つけたもの」・P3「計画からの変更」・スコープ外）。線のラベルのボタン（矢印の種類・×）も枠の中に落ち、中の線のボタンと重なる。
AI は段の流れを「受付 → 審査 → 通知 → 利用者へ戻る」のように書くので、戻る線はふつうに出てくる。

これを、**線がどちらの端も中にいない枠を横切らないように、枠の外を回して描く**ようにする。変えるのはエディタの線の描き方だけで、
保存（`Document.layout`）・コード生成・`read_diagram`・書き出し（merman）には何も足さない・変えない。

## 現況（2026-10-03、コードを読んで確かめた。画面での形は P0）

- 線は 1 種類（`edgeTypes.editableEdge` = `features/flowchart/components/edge/editable-edge.tsx` の `EditableEdge`）。道筋は xyflow の `getBezierPath`（出口と入口の 2 点と向きだけで決まる 3 次曲線）。
  **ほかのノード・枠の位置を見ない**。例外は枠の自己ループだけで、`frame-edit.ts:340` の `frameSelfLoopPath` が枠の右（左右の接続点なら下）の外を直角に回す（spec 16 P3）
- 接続点は置かれている入れ物の向きで決まる（spec 16 D6）。`TD` の図なら出口は下の辺、入口は上の辺。**下の枠から上のノードへ戻る線は、下へ出て上から入る**ので、
  曲線は出口から下へふくらみ、入口の上からかぶさるように、間にあるものを縦に貫く
- ラベルのボタンは曲線の中点（`getBezierPath` のラベル位置）に置かれ、`edge-layout.ts` の `adjustEdgeLabelPosition` が**互いに逆向きの線の組だけ**ずらす。枠・ノードとの重なりは見ない
- 線の重なりの順（xyflow 0.0.66 の `getElevatedEdgeZIndex`）: 線の高さは「端のノードのうち、親を持つものの高さ」の大きい方。
  **端が枠の中にある線は枠の中のノードと同じ高さで描かれ、図の直下のノード（高さ 0、背景が白）より上に出る見込み**（P0 の 4 で確かめる）。
  両端とも図の直下の線は高さ 0 で、枠（背景 `rgba(255,255,222,0.45)`）の下に透けて見える
- 枠の無い図でも、戻る線・段を飛ばす線は間のノードを貫く曲線で描かれる（フォーク元からの振る舞い）。ノードは背景が白で線より上なので、線はノードの後ろに隠れる（ボタンは隠れない）
- Mermaid の描画（mermaid.js の dagre、merman）は、段を飛ばす線・戻る線に途中の段の点（ダミーのノード）を置いて、間にあるノード・枠の横を通す — **記憶で、まだ確かめていない**（P0 の 2）
- xyflow 自身に障害物を避ける道筋は無い（React Flow の公式の例は Pro の libavoid）。障害物を避ける既製の部品に `react-flow-smart-edge`（格子の経路探索）がある。
  v12（`@xyflow/react`）で動くか・親ノード（枠）をどう扱うかは確かめていない（P0 の 3）

## 決めること

### D1. どの線を回すか（**裁定 1**）

- **案 A（推奨）: 「どちらの端も中にいない枠」と交わる線だけ**を回す。交わらない線は今の曲線のまま（枠の無い図は見た目が一切変わらない）。
  「中にいる」は端のノード・枠の祖先の枠（端が枠そのものなら、その枠と祖先）。端の祖先の枠は線が出入りするので障害物にしない
- 案 B: 案 A に加えて、**間のノードと交わる線**も回す。枠の無い図の戻る線も変わる（フォーク元の見た目が変わる。ノードの後ろに隠れているだけの線まで回すことになる）
- 案 C: 全部の線を障害物を避ける道筋にする（既製の部品をそのまま使う形）。交わらない線の形も変わる

推奨の理由: 見つけた問題は枠を貫くこと（枠は半透明で線もボタンも中に見える）。ノードは白で線を隠すので、案 B の得は小さく、Web 版の見た目の変化は大きい。
ただし**回した後の道筋はノードも避ける**（D2。回した線が別のノードを貫いては意味が無い）。P0 の 4 で、端が枠の中の線が図の直下のノードの上に描かれると分かれば、
その場合のノードとの交わりも案 A の対象に入れるかを rev1 で決める

交わりの判定: 今の曲線（`getBezierPath` と同じ式）を数十点に刻み、枠の矩形（見出しを含む外形）に点が入るか、隣り合う点を結ぶ線分が矩形を横切るかで見る。
線の両端の接続点が枠の縁に乗る場合（端そのものの枠）は障害物から外しているので当たらない

### D2. 回し方（**裁定 2**）

- **案 A（推奨）: 直角の回り道**（`frameSelfLoopPath` を一般化）。出口から接続点の向きへ 1 歩（20px）出て、横へ、**障害物の外側の縦の通り道**を通り、入口の手前 1 歩へ戻って入る。
  - 通り道の位置: 出口の 1 歩先と入口の 1 歩先の間の縦の範囲（`TD` なら y の範囲）に**かかる障害物**（D1 の枠と、その範囲のノード・枠のうち端の祖先でないもの）の外接の、右または左の外へ 40px
  - 右と左は**道のりが短い方**（同じなら右。`frameSelfLoopPath` と同じ）
  - `LR` / `RL` の図（接続点が左右）は縦と横を入れ替える（上か下を回る）
  - 同じ側を回る線が複数あると通り道が重なるので、**線の ID の順に 1 本ずつ 16px 外へずらす**（決まった順にして、描き直しで入れ替わらない）
  - ラベルのボタンは通り道の縦の中点（障害物の外）に置く。`adjustEdgeLabelPosition` のずらしは回した線にはかけない（通り道のずらしで足りる）
- 案 B: 既製の `react-flow-smart-edge` などの格子の経路探索。障害物を一般に避けられるが、依存が増え、格子の大きさで形と速さが変わる。
  親ノード（枠）は「中に入る線」の障害物から外す必要があり、部品がそれを扱えるかは P0 の 3 で見る
- 案 C: 曲線のまま、制御点を障害物の外へ出す。滑らかだが、制御点だけでは障害物の外を通ることを保証できない

推奨の理由: 回す線はまれで（戻る線・段を飛ばす線）、形が予測でき、純粋な関数でテストできる。自己ループの直しと同じ見た目になる。
Mermaid の描画（P0 の 2）が回り込む側（左右）と一致しなくても、エディタの線の道筋は保存も書き出しもしないので構わない

### D3. 計算の置き場所と描き直し

- 純粋な関数 `routeAroundFrames`（仮の名、`features/flowchart/utils/edge-route.ts`）: 入力は線の両端の ID・接続点の位置と向き・ノードと枠の絶対の矩形と親（`parentId`）。
  出力は「回さない」か「経路の点の列とラベルの位置」。`frameSelfLoopPath` もこの関数から呼ぶ形にまとめるかは P1 で決める（自己ループの形は変えない）
- `EditableEdge` では、`useStore` のセレクタで**障害物になりうる矩形を文字列の鍵**にして読む（spec 16 P3 の `selfLoopFrame` と同じ形。毎回新しいオブジェクトを返すとストアが変わるたびに描き直す）。
  ドラッグ中はノードが動くたびに全部の線が計算し直すので、**P0 の 5 で、ノード 100・線 150 の図で 1 回の計算の時間を測る**。重ければ、端か障害物が動いた線だけ計算する形を rev1 で足す
- 保存・コード生成・`read_diagram`・MCP・Rust・data_contract の名詞は変えない（表示だけ）。data_contract の `editor_frame` の説明に回り道の規則を 1 行足す

### D4. 変えないもの

- 交わらない線の形（D1 の案 A なら、枠の無い図の線は全部そのまま）
- 枠の自己ループ（spec 16 P3 の形）とノードの自己ループ（フォーク元の描き方）
- 互いに逆向きの線の組のラベルのずらし（`adjustEdgeLabelPosition`）— 回した線には効かせない（D2）
- 接続点の位置（spec 16 D6）

## 受け入れ条件

1. 枠を持つ図（`TD`・`LR`・`BT`・`RL`）で、線もラベルのボタンも、どちらの端も中にいない枠を横切らない（P0 の 1 の格子）
2. 回した線は、間にあるノードの矩形とも交わらない
3. 回す必要の無い線の形は変わらない。枠の無い図の線の形は全部変わらない（D1 の案 A の場合）
4. ノード・枠をドラッグすると、道筋が付いてくる（P0 の 5 で決めた大きさの図で、目に見える遅れが無い）
5. 保存ファイル・コード生成・`read_diagram` の出力は変わらない（表示だけの変更）
6. Web 版（GitHub Pages）のフローチャートのエディタで 1〜4 ができる（デスクトップ専用の変更を含まない）

## スコープ外

- 線どうしの交差を減らすこと、線をノードの縁に沿わせること
- 図全体・枠の中の並べ直し（spec 16 の裁定 4 のまま、枠の向きを変えた時だけ）
- 枠の並べ直しで広がった枠が隣と重なる・外から入る線のボタンが見出しに重なる（spec 16 P5 で見えたまま残したもの。別に起票する候補 ③）
- 線の接続点から枠の中へ落とした新しいノードを枠に入れること（候補 ②）
- merman が外とつながる枠へ短い線を描くこと（候補 ④、LORELEI.md の既知の制約）
- ER 図の線（`er-edge.tsx`）
