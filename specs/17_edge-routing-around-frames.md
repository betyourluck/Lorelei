# Spec: 枠をまたぐ線を、途中の枠の外へ回す

**ID**: 17
**Date**: 2026-10-03
**Status**: Draft（rev2。P0 の結果を反映（「P0 結果」）。裁定 1・2 と D4 の描き直しの形は利用者の裁定待ち）
**Branch**: 切らない（Phase 単位で main へ直接コミット）。spec 15・16 と同じく、**フォーク元の改善と台帳はコミットを分け**、フォーク元のコミットだけで上流へ PR を出せる形にする
（フォーク元のコミットは `lib/desktop/` と台帳を含まない。PR を出すか・いつ出すかは利用者が決める, CLAUDE.md）

## Goal

spec 16 で枠（サブグラフ）を指す線が描けるようになったが、**枠をまたいで戻る線（下の枠から上のノードへ）が、間にある枠の真ん中を貫いて描かれる**
（spec 16 P2「見つけたもの」・P3「計画からの変更」・スコープ外）。線のラベルのボタン（矢印の種類・×）も枠の中に落ち、中の線のボタンと重なる。
AI は段の流れを「受付 → 審査 → 通知 → 利用者へ戻る」のように書くので、戻る線はふつうに出てくる。段を飛ばす順向きの線（上のノードから間の枠を越えて下へ）も同じ形で貫く。

これを、**線がどちらの端も中にいない枠を横切らないように、枠とノードの外を回して描く**ようにする。変えるのはエディタの線の描き方（表示）だけで、
保存ファイル（`Document.layout`）・コード生成・`read_diagram`・書き出し（merman）の**出力とデータの形は変えない**。台帳は data_contract の `editor_frame` の説明文に回し方の規則を足す（D5）

## 現況（2026-10-03、コードを読んで確かめた。画面での形は P0）

- 線は 1 種類（`edgeTypes.editableEdge` = `features/flowchart/components/edge/editable-edge.tsx` の `EditableEdge`）。道筋は xyflow の `getBezierPath`（出口と入口の 2 点と向きだけで決まる 3 次曲線）。
  **ほかのノード・枠の位置を見ない**。例外は枠の自己ループだけで、`frame-edit.ts:340` の `frameSelfLoopPath` が、出口と入口が上下なら**いつも右**、左右なら**いつも下**の外を直角に回す（spec 16 P3。左右を選ぶ処理は無い, 査読 2-6）
- 接続点は**置かれている入れ物の向き**で決まる（spec 16 D6）。図の向きではなく、ノード・枠ごとに上下か左右かが違いうる。`TD` の入れ物なら出口は下の辺、入口は上の辺、`BT` なら逆、`LR` なら出口は右、入口は左、`RL` なら逆。
  **下の枠から上のノードへ戻る線（`TD`）は、下へ出て上から入る**ので、曲線は出口から下へふくらみ、入口の上からかぶさるように、間にあるものを縦に貫く
- ラベルのボタン（矢印の記号とラベル・矢印の種類・× の横並び。幅は 100px を超える）は曲線の中点に置かれ、`edge-layout.ts` の `adjustEdgeLabelPosition` が**互いに逆向きの線の組だけ**ずらす。枠・ノードとの重なりは見ない
- 線の描き直し: xyflow は線の端のノードが動いた時にその線を描き直す。`EditableEdge` の `selfLoopFrame`（`useStore` のセレクタ）は**自分の端の枠 1 つ**だけを読むので、無関係なノードが動いても描き直さない（査読 2-5）
- 線の重なりの順（xyflow 0.0.66 の `getElevatedEdgeZIndex`）: 線の高さは「端のノードのうち、親を持つものの高さ」の大きい方。
  **端が枠の中にある線は枠の中のノードと同じ高さで描かれ、図の直下のノード（高さ 0、背景が白）より上に出る**（P0 の 4 で確かめた。線の高さ = ノードの高さの時はノードが上で、線は隠れる）。
  両端とも図の直下の線は高さ 0 で、枠（背景 `rgba(255,255,222,0.45)`）の下に透けて見え、図の直下のノードの後ろには隠れる
- 枠の無い図でも、戻る線・段を飛ばす線は間のノードを貫く曲線で描かれる（フォーク元からの振る舞い）。両端とも図の直下なので、線はノードの後ろに隠れる（ボタンは隠れない）
- Mermaid の描画（mermaid.js の dagre、merman）は、輪をほどいて段組みを組み替え、戻る線・段を飛ばす線を枠の横に通す（P0 の 2 で確かめた。どちら側を回るかは並びで決まる）
- xyflow 自身に障害物を避ける道筋は無い（React Flow の公式の例は Pro の libavoid）。障害物を避ける既製の部品に `@tisoap/react-flow-smart-edge`（格子の A*）がある（P0 の 3）

## 言葉の定義（査読 1-1・1-9 を受けて、D1〜D4 で同じ意味に使う）

```text
端 e            = 線の source または target（ノードか枠）
祖先(e)         = e の parentId を根まで辿った枠の集まり（e 自身は含まない）
通れる枠(線)    = 祖先(source) ∪ 祖先(target)     … 線が出入りするので障害物にしない（見出しの帯だけは障害物, D2 の 6）
障害物(線)      = 図のノードと枠のうち、端でもなく 通れる枠(線) にも入らないもの
                  （矩形は絶対座標の外形。枠は見出しを含む。D3 の余白 MARGIN だけ外へ広げる）
回すか(線)      = 今の曲線が、障害物(線) のうち「回す対象」（裁定 1）のどれか、または端である枠の内側と交わる
道筋で避けるもの = 障害物(線) ∪ 端そのもの（ノード・枠。突き出しの外側だけを通る）∪ 通れる枠の見出しの帯
```

rev2 で直したこと（P0 の 5 の下書きを P0 の 1 の図に当てて分かった）: rev1 は端である枠を「通れる枠」に入れていたが、**端そのものは道筋では避ける**
（避けないと、入口のノードを下から貫いて上の接続点に入る道ができた）。また、戻る線は**自分の端の枠を縦に貫く**（`TD` の a で、通知 → 利用者の曲線は通知の中も通る）ので、
端である枠の内側との交わりも「回すか」に入れる

- **「回すか」と「避けるもの」は別の集まり**: 回すかどうかは裁定 1 の対象（枠だけ、など）との交わりで決め、**回すと決めた線の道筋は 障害物(線) の全部（ノードも枠も）を避ける**。
  回した線が別のノードを貫いては意味が無いので、避けるものは裁定に関わらずいつも全部にする（査読 1-1）
- 交わりの判定は、今の曲線（`getBezierPath` と同じ式）を刻んだ折れ線の各線分が矩形を横切るか・矩形の中に点があるかで見る。刻みの数は P0 の 5 で決める（線の長さに比例、下限あり）

## 決めること

### D1. どの線を回すか（**裁定 1**。「回す対象」を決める）

- **案 A（推奨）: 枠と、線より下に描かれるノード** — 今の曲線が 障害物(線) のうち**枠**、または**線の高さより低いノード**と交わる線を回す。交わらない線は今の曲線のまま
  - 「線の高さ」は xyflow の `getElevatedEdgeZIndex` と同じ（端のうち親を持つものの高さの大きい方）、ノードの高さは xyflow の `internals.z`。
    P0 の 4 で、**線の高さ > ノードの高さの時だけ線がノードの上に見え、同じ高さならノードが線を隠す**と確かめた（rev1 の「確かめられたら」の分岐を、この条件で確定させた, 査読 1-2）。
    両端とも図の直下の線（高さ 0）は、ノードとの交わりでは回さない
- 案 B: 枠とノードの両方 — 枠の無い図の戻る線・飛ばす線も回る（フォーク元の Web 版の見た目が変わる。ノードの後ろに隠れているだけの線まで回す）
- 案 C: 全部の線を障害物を避ける道筋にする（交わらない線の形も変わる）

推奨の理由: 見つけた問題は枠を貫くこと（枠は半透明で線もボタンも中に見える）。図の直下どうしの線はノードの後ろに隠れ、案 B の得は小さく、Web 版の見た目の変化は大きい

- **戻る線と段を飛ばす順向きの線の両方が対象**（査読 2-1）。区別は流れの向きではなく、曲線が障害物と交わるかどうかだけで決める（回す必要の無い順向きの線は今の曲線のまま）

### D2. 回し方（**裁定 2**）

rev0 の案 A（出口から 1 歩出て、縦の通り道 1 本で回る 5 本の線分）は、**横の線分が障害物を横切りうる**（出口・入口の高さに横並びのノードや枠がある時、
端が枠の中で同じ枠の中のノードを横切って出る時。査読 1-7・2-2・2-3）ので、受け入れ条件 1・2 を保証できない。**外した**。

- **案 A（推奨）: 直交の経路探索（自前の純粋な関数）**。障害物(線) を MARGIN だけ広げた矩形の集まりの中で、縦と横の線分だけの道筋を探す:
  1. 出口から接続点の向きへ**突き出し**（STUB）を出し、入口にも接続点の向きの反対から入る突き出しを付ける。突き出しは接続点の向きで決める（4 方向とも同じ規則。`TD`・`BT`・`LR`・`RL` の表を作らない — 接続点の向きは入れ物ごとに違うので、図の向きでは決められない, 査読 1-6・2-6）。
     **突き出しの先が障害物の中に入る時は、障害物の外に出るまで伸ばす**。伸ばしても出られない（接続点が障害物に埋まっている）時は、その線は回さず今の曲線のまま（査読 1-11）
  2. 突き出しの先どうしを、**障害物の広げた矩形の辺の延長線**の交点だけを点とする格子（直交の見通しの格子）の上で、道のり + 曲がり 1 回あたりの重み（BEND_COST）が最小の道で結ぶ。
     障害物を 1 つの外接の矩形にまとめない（離れた 2 つの枠の間の隙間も通れる, 査読 1-6）。左右・上下のどちらを回るかもこの最小で決まる（「短い方」の式 = 道のり + BEND_COST × 曲がりの数）。同じ重みなら、右・下を先に取る（決まった順）
  3. 道が見つからない時は今の曲線のまま（P0 の 1 の格子では起きないことを確かめる）
  4. 角は半径 CORNER の丸めで描く（xyflow の `getSmoothStepPath` と同じ見た目に寄せる。回さない線の曲線と並んでも浮かないように, 査読 2-1）
  5. 探索の状態は「点 × 来た向き（4 方向）」で持ち、**来た向きと逆へは進まない**。入口へは接続点の向きの反対から入る（P0 の 5: 2 方向で持つと、突き出しの先で 180° 折り返して戻る道ができた）
  6. **通れる枠の見出しの帯（上の辺から 28px、題・ID・向きのメニュー・×）は避ける**。通れる枠からは横か下の辺から出入りする
     （P0 の 5: 下書きは、枠の中の端から出る線を通れる枠の縁の内側に沿わせ、見出しの題の横を横切らせた）。
     見出しの帯を避けると出られない形（枠の横と下が詰まっている）は 3 と同じく今の曲線
- 案 B: 既製の `@tisoap/react-flow-smart-edge`（格子の A*）。端の祖先の枠を障害物から外す処理は持っている（P0 の 3）が、回すかの判定が**直線と全部のノード**で、裁定 1 の対象と合わない。
  既定は Web Worker で非同期に計算し、その間は普通の線を出す（取り込み直後・ドラッグ中に線が切り替わって見える）。回した線どうしの重なりを離す処理は説明に無い
- 案 C: 曲線のまま、制御点を障害物の外へ出す。滑らかだが、制御点だけでは障害物の外を通ることを保証できない

推奨の理由: 受け入れ条件 1・2 を道筋の作り方そのもので保証でき、純粋な関数でテストできる。回す線はまれ（戻る線・段を飛ばす線）なので、探索は回す線だけにかければよい。
Mermaid の描画（P0 の 2）と回る側（左右）が一致しなくても、エディタの線の道筋は保存も書き出しもしないので構わない

### D3. 回した線どうしの重なりとラベルのボタン

- **回した線どうしが同じ線分の上に重なる時だけ**、平行な線分を SPACING ずつ離す（重なる線分の組ごとに、**幾何の順**（縦の線分なら左から、横の線分なら上から、元の位置の順）で並べ、同じ位置なら線の ID の順。描き直しで入れ替わらない, 査読 1-8）。
  線どうしの交差を減らすことはしない（スコープ外。離すのは「回した線が完全に重なって 1 本に見える」場合だけ, 査読 1-5）
- ラベルのボタンは、回した線の**一番長い線分の中点**に置く（縦横どちらの線分でも同じ規則。`LR` でも成り立つ, 査読 1-8）。
  **ボタンの矩形（P0 の 6 で測る幅と高さ）が 障害物(線) やほかの回した線のボタンと重なる時は**、同じ線分の上で重ならない位置へずらす（線分の中で、中点に近い順に BUTTON_GAP 刻みで試す）。
  どこでも重なる時は次に長い線分へ。それでも無ければ中点のまま（P0 の 1 の格子では起きないことを確かめる）
- `adjustEdgeLabelPosition`（互いに逆向きの組のずらし）は回した線にはかけない。互いに逆向きの組の両方を回した時のボタンの重なりは、上のボタンの重なりの規則が扱う（査読 1 の提案 3・査読 2-6）。
  片方だけ回した組は、回さなかった方に今のずらしが残る
- 定数（STUB・MARGIN・SPACING・BEND_COST・CORNER・BUTTON_GAP）は名前を付けて 1 か所に置く（査読 1-8）。P0 の 5・6 の測りからの初めの値（P1 の画面で直す）:
  STUB 20（自己ループと同じ）・MARGIN 12・BEND_COST 40・CORNER 8・SPACING 8・BUTTON_GAP 8。
  根拠: 横に並ぶ枠の間は `MIN_GAP` 30（`nested-layout.ts`）なので、MARGIN 12 で 6px の通り道が残り、SPACING 8 でも 2 本までは離せる。段の送りはノードどうし 102。
  ボタンは 101×28（ラベルが空）〜 1 行のまま伸びる（長いラベルで 330×28）ので、30px の隙間の縦の線分には置けず、ボタンの重なりの規則で横の線分へ移る見込み

### D4. 計算の置き場所と描き直し（査読 1-9・2-4・2-5）

- 線どうしの重なり（D3）を決めるには全部の線が要るので、**線 1 本ずつではなく、図全体で 1 回に計算する**:
  `routeEdges(nodes, edges, sides) → Map<線の ID, 経路>`（仮の名、`features/flowchart/utils/edge-route.ts`）。
  - 入力: 全部のノード・枠（絶対の矩形と `parentId`。祖先は関数の中で `parentId` を根まで辿る）・全部の線（ID・両端）・各端の接続点の位置と向き（`sides` は spec 16 D6 の向きの表から作る）。図の向きは渡さない（接続点の向きで足りる）
  - 出力: 回す線だけの「点の列とラベルの位置」。入っていない線は今の曲線
  - 手順: (1) 全部の線で「回すか」を判定（曲線を刻んで交わりを見るだけで、軽い）(2) 回す線だけ D2 の探索 (3) D3 の重なりとボタンの位置
  - `frameSelfLoopPath` はそのまま残し、枠の自己ループは `routeEdges` の対象から外す（形を変えない）
- 描き直しの形は P0 の 5 の測りで決める（rev0 の「`useStore` のセレクタで障害物の矩形を文字列の鍵に」は、全部のノードを鍵にすると**どのノードを動かしても全部の線が描き直す**ので外した, 査読 2-5）:
  - 案 i: エディタで `routeEdges` を 1 回呼び、結果を小さなストア（線の ID ごとに購読できる形）で渡す。線は自分の経路が変わった時だけ描き直す
  - 案 ii: 案 i に加えて、ドラッグ中は計算を間引く（例えば 1 フレームに 1 回、または重ければ 50ms に 1 回）。ドラッグを終えた時は必ず計算し直す
  - **案 iii（rev2 で足した。推奨）**: 案 i の形で、ドラッグ中は**動いたノード・枠と関わる線だけ**を計算し直す
    （端が動いた線、今の道筋か曲線の外接の矩形に動いたものが入る・出る線）。ほかの線の経路はそのまま。ドラッグを終えた時は全部を計算し直す（重なりの離し方 D3 は全部を見ないと決まらない）
  - P0 の 5 の測り（node 24、使い捨ての下書き、ノード 100・枠 10・線 150。回すかの判定だけなら 0.9ms、回す線 1 本あたりの探索がおよそ 1ms）:
    裁定 1 の案 A に近い「枠だけ」で回す線 8 本・中央値 7.5〜8.7ms（最大 16ms）、案 B「枠とノード」で 15 本・13.3ms（最大 17ms）。
    1 フレーム（16ms）に収まるが、ドラッグ中は React の描き直しも同じフレームに入るので、毎フレーム全部を計算する案 i は余裕が無い。
    ドラッグ中に動くのは 1 つのノード・枠で、関わる線は数本なので、案 iii なら 1 フレームに数 ms で済む見込み。**ブラウザでの時間は P1 で測る**（下書きは node での値）

### D5. 変えないもの・台帳

- 「回すか」に当たらない線の形（今の曲線のまま）
- 枠の自己ループ（spec 16 P3 の形）とノードの自己ループ（フォーク元の描き方）
- 接続点の位置（spec 16 D6）
- 保存ファイル・コード生成・`read_diagram`・MCP・Rust の出力とデータの形。data_contract の名詞は足さない。`editor_frame` の説明文に「枠をまたぐ線の回し方」（言葉の定義・裁定 1 の対象・D2 の探索・D3 の重なり）を書き足す（査読 1-3）

     DOM の線の `path` を刻んで、どの枠・ノードの矩形と交わるか、ラベルのボタンがどの枠・ノードの中にあるか（窓を前に出してもらう, failures #26）。**P1 のテストの正解表にする**

## 受け入れ条件

判定は**最終の道筋**（回した線は回した後の折れ線、回さない線は今の曲線）と**ボタンの矩形**で行う（元の曲線との交わりではない, 査読 1 の提案 2）。

1. 枠を持つ図（入れ物の向き `TD`・`BT`・`LR`・`RL`、P0 の 1 の格子）で、線の最終の道筋とラベルのボタンが、どちらの端も中にいない枠（= 障害物(線) の枠）を横切らない
2. 回した線の最終の道筋とボタンは、障害物(線) のノードとも交わらない。回した線どうしのボタンも重ならない
3. 「回すか」に当たらない線の形は変わらない（裁定 1 の対象は rev2 で確定させ、ここで参照する）
4. ノード・枠をドラッグすると、道筋が付いてくる（ノード 100・枠 10・線 150 の図で、D4 で決めた間隔より遅れない）。ドラッグを終えた時の道筋は 1・2 を満たす
5. 保存ファイル・コード生成・`read_diagram` の出力は変わらない（表示だけの変更）
6. Web 版（GitHub Pages）のフローチャートのエディタで 1〜4 ができる（デスクトップ専用の変更を含まない）

## スコープ外

- 線どうしの交差を減らすこと、回さない線どうしの重なり（回した線どうしが同じ線分に重なる時だけ離す, D3）、線をノードの縁に沿わせること
- 図全体・枠の中の並べ直し（spec 16 の裁定 4 のまま、枠の向きを変えた時だけ）
- 枠の並べ直しで広がった枠が隣と重なる・外から入る線のボタンが見出しに重なる（spec 16 P5 で見えたまま残したもの。別に起票する候補 ③。回した線のボタンは D3 で障害物を避けるが、回さない線のボタンは今のまま）
- 線の接続点から枠の中へ落とした新しいノードを枠に入れること（候補 ②）
- merman が外とつながる枠へ短い線を描くこと（候補 ④、LORELEI.md の既知の制約）
- ER 図の線（`er-edge.tsx`）
